## 二、间隔复盘

- `GC Roots` 是可达性分析的起点。栈帧局部变量、静态字段、活动线程和 JNI 引用等都可能成为 GC Roots；无法从 GC Roots 到达的对象可以被回收。
- JVM 采用分代收集，是因为大多数对象生命周期短。高频回收新生代可以减少扫描整个堆的成本。
- Young GC 主要回收新生代；G1 的 Mixed GC 回收新生代和部分老年代 Region；Full GC 通常回收范围很大，停顿风险较高。
- G1 会优先选择垃圾比例高、存活对象少、回收收益高的 Region，因此称为 Garbage First。

## 三、JVM 常用参数

| 参数 | 作用 | 我的理解 |
|---|---|---|
| `-Xms` | 初始堆大小 | JVM 启动时堆的初始容量。 |
| `-Xmx` | 最大堆大小 | JVM 堆允许扩展到的最大容量。 |
| `-Xss` | 单个线程栈大小 | 控制每个线程的虚拟机栈大小；过小可能导致 `StackOverflowError`，过大会减少可创建线程数。 |
| `-XX:MetaspaceSize` | 元空间触发 GC 的初始阈值 | 元空间达到该阈值时，JVM 会尝试通过 GC 和类卸载回收元数据。 |
| `-XX:MaxMetaspaceSize` | 元空间最大限制 | 限制元空间上限；设置过小可能导致 `Metaspace OOM`。 |
| `-XX:+HeapDumpOnOutOfMemoryError` | OOM 时自动生成堆转储 | 用于保留 OOM 现场，分析大对象和到 GC Roots 的引用链。 |
| `-XX:HeapDumpPath` | 指定堆转储输出路径 | 指定 Heap Dump 的保存目录或文件路径，并确保磁盘空间充足。 |
| `-Xlog:gc*` | 输出 GC 日志 | 输出收集器、GC 类型、触发原因、内存变化和停顿时间等信息。 |
| `-XX:+UseG1GC` | 指定使用 G1 收集器 | 显式选择 G1；当前实验日志已确认使用 G1。 |

### 参数边界

```text
-Xmx 不是越大越好。
堆大小需要结合容器内存、并发量、停顿目标、元空间和其他进程的内存共同评估。
```

## 四、GC 日志阅读

### 固定阅读顺序

```text
收集器
-> GC 类型
-> 触发原因
-> 回收前后堆占用
-> Eden / Survivor / Old / Humongous Region 变化
-> 停顿耗时
```

### 本次日志分析

```text
收集器：G1
GC 类型：Young GC
触发原因：G1 Humongous Allocation
堆内存变化：13M->4M(32M)，本次回收约 9MB
Region 变化：Eden 1->0，Survivor 0->1，Old 6->6，Humongous 8->0
停顿耗时：1.042ms
结论：本实验中持续创建 1MB 数组，触发大对象分配；大对象 Region 被回收，老年代没有增长，因此这是正常实验负载，不是内存泄漏。
```

### 常见判断

| 现象 | 初步判断 |
|---|---|
| GC 后堆占用明显下降 | 可能是正常的高对象分配压力。 |
| GC 后老年代仍持续上涨 | 需要怀疑内存泄漏、缓存失控或对象长期持有。 |
| Young GC 频率过高 | 对象分配过快、Eden 较小或存在大量临时对象。 |
| Full GC 频繁且回收效果差 | 优先排查老年代压力、泄漏、大对象和堆配置。 |

## 五、OOM 基础排查

### 1. 常见 OOM 类型

| 类型 | 常见原因 |
|---|---|
| `Java heap space` | 大对象、集合持续增长、缓存失控、内存泄漏、堆过小。 |
| `Metaspace` | 动态生成大量类、类加载器无法卸载。 |
| `Direct buffer memory` | 堆外直接内存持续占用。 |
| `unable to create native thread` | 线程过多、系统线程资源不足。 |

### 2. 基础排查链路

```text
1. 确认 OOM 类型或 Full GC 现象
2. 查看 GC 日志和监控趋势
3. 判断 GC 后内存是否能够下降
4. 开启 Heap Dump，保留 OOM 现场
5. 分析占用内存最多的对象及引用链
6. 回到代码排查缓存、静态集合、ThreadLocal、批量查询、监听器、类加载器
```

### 3. 我的理解

```text
Heap OOM 的核心是 Java 对象或数组占满堆，排查时重点分析 Heap Dump 中占用内存最多的对象和到 GC Roots 的引用链。

Metaspace OOM 的核心是类元数据空间不足，重点排查动态代理、动态类生成和 ClassLoader 是否无法卸载。

频繁 Full GC 时，应先确认触发原因和 GC 后老年代是否下降，再决定是排查泄漏、高分配率、大对象还是堆配置。
```

## 七、算法题：合并区间

### 解题思路

```text
先按区间起点升序排序。

排序后，后续区间只需要和结果列表中的最后一个区间比较：
- 当前区间起点大于最后区间终点：没有重叠，直接加入结果。
- 否则存在重叠：将最后区间终点更新为两者终点的最大值。

排序保证了可能合并的区间会相邻出现，因此只需一次遍历。
```

### Java 代码

```java
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;

class Solution {
    public int[][] merge(int[][] intervals) {
        if (intervals.length == 0) {
            return new int[0][];
        }

        Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0]));

        List<int[]> mergedList = new ArrayList<>();

        for (int[] interval : intervals) {
            if (mergedList.isEmpty()
                    || mergedList.get(mergedList.size() - 1)[1] < interval[0]) {
                mergedList.add(interval);
            } else {
                int[] lastInterval = mergedList.get(mergedList.size() - 1);
                lastInterval[1] = Math.max(lastInterval[1], interval[1]);
            }
        }

        return mergedList.toArray(new int[0][]);
    }
}
```

### 复杂度

```text
时间复杂度：O(n log n)，主要来自排序。
空间复杂度：O(n)，最坏情况下 mergedList 保存全部区间，排序也可能需要额外辅助空间。
```

## 八、面试口述

### 题目 1：`-Xms`、`-Xmx`、`-Xss` 分别控制什么？为什么 `Xmx` 不能盲目调大？

```text
-Xms 控制初始堆大小，-Xmx 控制最大堆大小，-Xss 控制单个线程栈大小。

-Xmx 不是越大越好。堆过大会占用更多容器内存，也可能导致 GC 时扫描和停顿成本增大。堆大小需要结合容器内存、并发量、停顿目标、元空间和其他进程内存共同评估。
```

### 题目 2：线上频繁 Full GC，你会按什么顺序排查？

```text
线上频繁 Full GC 时，我会先通过 GC 日志和监控确认频率、停顿和触发原因，再重点观察 Full GC 后老年代是否下降。

如果回收后内存仍持续上涨，优先怀疑内存泄漏；如果能明显下降但很快又涨满，则排查高分配率、批量任务、大对象和堆配置。

随后保留 GC 日志和 Heap Dump，通过对象占用和到 GC Roots 的引用链定位静态缓存、ThreadLocal、批量查询或类加载器等问题。根因修复后，最后才评估堆大小和收集器参数。
```

### 题目 3：Heap OOM 和 Metaspace OOM 的常见原因有什么不同？

```text
Heap OOM 是堆中的 Java 对象或数组占满内存，常见于缓存失控、静态集合、ThreadLocal、批量查询和大对象。

Metaspace OOM 是类元数据空间不足，通常由动态生成大量类、热部署或自定义类加载器泄漏导致。

排查 Heap OOM 主要分析 Heap Dump 中的大对象和引用链；排查 Metaspace OOM 则重点检查类数量、动态代理和 ClassLoader 是否无法卸载。
```
