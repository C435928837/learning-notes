## 2. Redis 常用数据结构总览

| 数据结构 | 核心特点 | CloudMall 示例 |
| --- | --- | --- |
| `String` | 存储单个完整值或数值计数器 | 商品详情 JSON、商品浏览量 |
| `Hash` | 一个 Key 下存多个字段 | 商品对象的字段独立读写 |
| `List` | 有序、可重复、两端操作 | 非核心异步通知任务 |
| `Set` | 无序、元素天然去重 | 用户收藏的商品 ID |
| `ZSet` | 成员唯一，按 `score` 有序 | 商品热度榜 |

同一个 Redis Key 只能对应一种数据结构。已用 `String` 保存 JSON 的 `product:P001`，不能再使用 `HSET product:P001 ...`，否则 Redis 会返回 `WRONGTYPE`。

## 3. String：完整值与原子计数

### 3.1 商品详情缓存

```text
Key：product:detail:P001
Value：{"productCode":"P001","productName":"机械键盘","price":299.00}
结构：String + JSON
```

商品详情通常整体查询、整体返回。读取后反序列化即可作为接口响应返回前端，因此常使用 `String + JSON`。

```redis
SETEX product:detail:P001 1800 '{"productCode":"P001","productName":"机械键盘","price":299.00}'
GET product:detail:P001
```

数据库仍是事实来源。商品更新时遵循 Cache Aside：先更新数据库，成功后删除缓存，由后续读取回填新缓存。

### 3.2 商品浏览量

```text
Key：product:view-count:P001
Value：1024
结构：String
```

```redis
INCR product:view-count:P001
INCRBY product:view-count:P001 5
```

`INCR` 是 Redis 单命令原子操作，多个请求并发递增不会丢失更新，适合商品浏览量、点赞数、限流计数等场景。浏览量可通过消息队列或定时任务异步持久化到数据库。

### 3.3 单命令原子性与库存边界

以下做法不能安全扣库存：

```text
GET product:stock:P001
判断库存是否大于 0
DECR product:stock:P001
```

原因是 `GET` 和 `DECR` 虽然各自原子，但“判断后扣减”由多条命令组成。库存为 `1` 时，两个请求都可能读到 `1` 并先后扣减，最终库存变为 `-1`。

库存扣减应使用 Lua 脚本将“库存是否足够 + 扣减数量”作为一个原子操作执行：

```lua
local stock = tonumber(redis.call('GET', KEYS[1]))

if not stock or stock < tonumber(ARGV[1]) then
    return 0
end

redis.call('DECRBY', KEYS[1], ARGV[1])
return 1
```

```text
KEYS[1]：product:stock:P001
ARGV[1]：购买数量
返回 1：扣减成功
返回 0：库存不足
```

Lua 脚本在 Redis 服务端整体执行，其他客户端命令不会插入到“判断库存”和“扣减库存”之间。

Redis 扣减成功不等于订单一定创建成功。生产上还需要订单幂等、失败补偿或回滚、可靠消息投递、对账，以及数据库条件更新等兜底措施。

## 4. Hash：对象字段独立读写

```redis
HSET product:admin:P001 name "机械键盘" price 299.00 category "keyboard"
HGET product:admin:P001 price
HSET product:admin:P001 price 319.00
HGETALL product:admin:P001
```

`Hash` 适合对象的某些字段频繁独立读取或更新。例如后台只修改商品价格时，可以仅执行 `HSET ... price ...`，不必读取、修改、再整体写回 JSON。

取舍：商品详情接口多为整体读取与整体返回，通常优先 `String + JSON`；字段独立变更频繁时，可考虑 `Hash`。无论选择哪种缓存结构，都要保持 Key 命名清晰，避免同一个 Key 混用结构。

---

## 5. Set：用户收藏去重

```text
Key：user:favorite:1001
Value：{P001, P002, P003}
```

```redis
SADD user:favorite:1001 P001
SREM user:favorite:1001 P001
SISMEMBER user:favorite:1001 P001
SMEMBERS user:favorite:1001
```

用户不能重复收藏同一个商品，`Set` 的元素唯一性正好满足该需求。它不保证排序；若收藏列表必须按收藏时间排序，应使用 `ZSet`，将收藏时间作为 `score`。

---

## 6. ZSet：商品热度榜

```text
Key：product:hot-rank
Member：P001
Score：浏览量或综合热度
```

```redis
ZINCRBY product:hot-rank 1 P001
ZREVRANGE product:hot-rank 0 9 WITHSCORES
```

`ZINCRBY` 原子增加商品热度；`ZREVRANGE` 按 `score` 从高到低返回 Top N。普通 `String` 可以记录每件商品的单独浏览量，但不擅长直接生成排行；`ZSet` 同时解决计分和排序。

Redis 热度榜适合实时展示。长期统计、复杂筛选和永久留存仍需要异步落库或进入分析系统。

---

## 7. List：简单异步任务队列

```redis
LPUSH order:notify-tasks orderNo-202608250001
BRPOP order:notify-tasks 30
```

`List` 有序且允许重复，可通过一端写入、另一端取出组成简单队列。`BRPOP` 可在没有任务时阻塞等待，避免消费者持续轮询。

CloudMall 的非核心短信通知、缓存刷新等任务可以考虑 Redis List。但它不等于可靠消息队列：消费者取出任务后异常宕机可能丢失任务，且缺少完善的确认、重试、死信和消费进度能力。

订单、支付、库存最终一致性等核心链路不能仅依赖 Redis List。下单时应先完成核心库存预占或扣减与订单落库；后续通知、积分等异步事件使用可靠消息队列，并配合幂等、重试、补偿和对账。

## 8. CloudMall 选型总结

| 场景 | Redis 结构 | 关键命令/原因 | 边界 |
| --- | --- | --- | --- |
| 商品详情缓存 | `String + JSON` | 整体读写，反序列化后可直接返回 | 数据库更新成功后删除缓存 |
| 商品浏览量 | `String` | `INCR` 原子递增 | 异步落库；不能替代库存扣减 |
| 用户收藏 | `Set` | `SADD` 天然去重，`SISMEMBER` 判断是否收藏 | 无序；需按时间排序时改用 `ZSet` |
| 商品热度榜 | `ZSet` | `ZINCRBY` 增加分数，`ZREVRANGE` 查询 Top N | 统计和长期数据需落库 |
| 非核心异步通知 | `List` | `LPUSH` + `BRPOP` 简单队列 | 不具备可靠消息队列完整保障 |

## 10. 面试表达

### Redis 常用数据结构在 CloudMall 中如何选择？

商品详情缓存使用 `String + JSON`，因为详情通常整体读取和整体返回；商品浏览量使用 `String` 的 `INCR`，因为它能原子递增；用户收藏使用 `Set`，保证商品 ID 去重；商品热度榜使用 `ZSet`，以商品 ID 为成员、热度为 `score`，通过 `ZINCRBY` 增加热度并通过 `ZREVRANGE` 获取 Top N；非核心异步通知可以使用 `List` 组成简单队列。Redis 负责高性能访问和展示，核心数据仍需要落库，并处理缓存过期、重启和一致性边界。

### 为什么浏览量适合 INCR，而库存扣减不能只用 DECR？

`INCR` 适合单变量的原子累加。库存扣减还包含“库存是否足够”的业务判断，`GET + 判断 + DECR` 是多命令流程，可能在中间被其他请求穿插并造成负库存。应使用 Lua 脚本把判断和扣减整体原子执行，并在订单侧补充幂等、补偿、对账和数据库兜底。
