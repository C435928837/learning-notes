## 2. 为什么需要消息队列

若订单服务在用户下单后同步调用所有后续服务：

```text
创建订单
→ 扣减库存
→ 发送短信
→ 增加积分
→ 初始化物流
→ 更新营销统计
→ 返回下单结果
```

会产生以下问题：

- 短信、物流等非核心服务变慢，会拖慢下单接口。
- 非核心服务故障，可能错误地让用户下单失败。
- 大促高峰时，各服务同时接收请求，容易被瞬时流量压垮。
- 订单服务直接依赖多个下游服务，新增业务会侵入订单核心代码。

使用 RabbitMQ 后：

```text
订单服务完成核心下单
→ 发布 order.created 事件
→ RabbitMQ 路由到不同业务队列
→ 积分、短信、物流、统计服务各自异步消费
```

| 能力 | 含义 | CloudMall 场景 |
| --- | --- | --- |
| 异步 | 下单接口不等待非核心任务 | 短信、积分、物流初始化 |
| 解耦 | 订单服务不直接调用每个下游服务 | 新增营销服务时不改订单主流程 |
| 削峰 | 高峰请求先进入队列，消费者按处理能力消费 | 大促期间平滑处理通知和积分 |

消息队列不是数据库事务，也不能天然保证业务只执行一次。订单、库存等核心状态仍需要同步链路中的原子扣减、幂等、数据库约束、补偿和对账保障。

```text
同步核心链路：库存预占或扣减、创建订单、订单幂等校验
异步后续链路：短信通知、增加积分、物流初始化、营销统计
```

## 3. RabbitMQ 核心模型

```text
Producer
  ↓ 发布消息，携带 Routing Key
Exchange
  ↓ 根据 Binding 路由规则
Queue
  ↓
Consumer
```

| 角色 | 是什么 | CloudMall 示例 |
| --- | --- | --- |
| Producer | 发送消息的应用 | 订单服务发布订单创建事件 |
| Exchange | 路由中心，决定消息进入哪些 Queue | `order.event.topic` |
| Queue | 暂存等待处理的消息 | `order.points.queue` |
| Binding | Exchange 到 Queue 的路由规则 | `order.created -> order.points.queue` |
| Routing Key | Producer 发送消息时携带的路由标签 | `order.created` |
| Consumer | 从 Queue 获取并处理消息的应用 | 积分服务、短信服务 |

Exchange 不保存消息，Queue 才保存消息；Binding 不是消息，而是路由规则。

### 3.1 订单创建事件示例

Producer 发送：

```text
Exchange：order.event.topic
Routing Key：order.created
消息体：{ "orderNo": "O001", "userId": 1001 }
```

预先声明 Binding：

```text
order.created -> order.sms.queue
order.created -> order.points.queue
```

消息的 Routing Key 匹配这两条 Binding，因此 RabbitMQ 会分别向短信队列和积分队列投递一份消息。Exchange 通过 Binding 将消息路由到零个或多个 Queue。[RabbitMQ AMQP Model](https://www.rabbitmq.com/tutorials/amqp-concepts)

## 4. 三种常用 Exchange

| 类型 | 路由规则 | CloudMall 示例 |
| --- | --- | --- |
| `direct` | Routing Key 与 Binding Key 完全相等 | 固定事件 `order.created` 精确投递 |
| `fanout` | 忽略 Routing Key，广播给全部绑定队列 | 全站活动状态变化通知 |
| `topic` | 按点号分段，使用通配规则匹配 | 订单事件分类订阅 |

### 4.1 direct：精确匹配

```text
消息 Routing Key：order.created
Binding Key：order.created
→ 匹配

消息 Routing Key：order.cancelled
Binding Key：order.created
→ 不匹配
```

多个 Queue 可以绑定同一个 Binding Key，因此 `direct` 也可以把一条消息发给多个匹配的队列。

### 4.2 fanout：广播

```text
system.broadcast.fanout
  ├─ cache.refresh.queue
  ├─ audit.log.queue
  └─ monitor.event.queue
```

消息发送到 `fanout` Exchange 后，会复制到所有绑定 Queue，Routing Key 被忽略。

### 4.3 topic：通配匹配

`topic` 将 Routing Key 和 Binding Key 按 `.` 拆分成多个单词：

```text
order.created      -> order / created
order.paid.success -> order / paid / success
```

通配符：

```text
*：恰好匹配一个单词
#：匹配零个、一个或多个单词
```

| Binding Key | 能匹配 | 不能匹配 |
| --- | --- | --- |
| `order.*` | `order.created`、`order.paid` | `order`、`order.paid.success` |
| `order.#` | `order`、`order.created`、`order.paid.success` | `payment.success` |
| `order.paid.*` | `order.paid.success` | `order.paid`、`order.paid.success.notify` |

例如审计队列需要接收所有订单事件：

```text
Binding Key：order.#
```

物流队列只关心已支付事件：

```text
Binding Key：order.paid
```

若事件细分为 `order.paid.success`，可以按实际需求使用完整 Key 或 `order.paid.*`。`topic` 的 `*` 匹配一个分段，`#` 匹配零个或多个分段；`fanout` 则忽略 Routing Key 并向全部绑定 Queue 复制消息。[RabbitMQ Exchanges](https://www.rabbitmq.com/docs/exchanges)

## 5. 消费者确认与幂等

### 5.1 为什么使用手动 ack

自动确认会在 Broker 把消息发给消费者后立即认为消息处理成功。若消费者还未完成数据库操作就宕机，消息可能丢失。

手动确认的正确顺序：

```text
RabbitMQ 投递积分消息
→ 积分服务按 orderNo 执行业务
→ 数据库操作成功
→ Consumer 发送 ack
→ Broker 删除消息
```

若消费者在 `ack` 前宕机或网络断开，Broker 没有收到确认，消息可以重新投递。

### 5.2 为什么手动 ack 仍需要幂等

```text
1. 积分服务已成功为订单 O001 增加 100 积分
2. Consumer 发送 ack 前网络断开
3. Broker 未收到 ack，重新投递 O001
4. Consumer 再次收到 O001
```

因此消费者必须按 `orderNo` 或业务事件 ID 去重：

```text
已处理过 O001
→ 不再增加积分，直接 ack

未处理过 O001
→ 增加积分并记录消费结果
→ ack
```

```text
手动 ack：降低消息丢失风险
幂等处理：防止消息重复执行业务
```

显式确认模式下，Broker 在收到 Consumer 的确认前不会完全删除消息；未确认的消息在消费者异常时可被重新投递。[RabbitMQ AMQP Model](https://www.rabbitmq.com/tutorials/amqp-concepts)

## 6. 多消费者与多 Queue

### 6.1 同一个 Queue 的多个消费者：竞争消费

```text
order.points.queue
  ├─ 积分服务实例 A
  ├─ 积分服务实例 B
  └─ 积分服务实例 C
```

同一个 Queue 中的一条积分消息只会由其中一个实例处理。多个实例共同分摊同一种业务的消费压力，实现横向扩展。

```text
不是广播，而是竞争消费。
```

### 6.2 多个 Queue：不同业务各自消费

```text
order.event.topic
  ├─ order.sms.queue
  ├─ order.points.queue
  └─ order.logistics.queue
```

当多条 Binding 都匹配同一条订单事件时，每个匹配 Queue 都会收到一份消息，供不同业务独立处理。

```text
同一个 Queue 的多个消费者：分摊同一种业务处理压力
多个 Queue：让不同业务获得各自的一份消息
```

积分服务部署 3 个实例时，应让它们监听同一个 `order.points.queue`。若创建 3 个积分 Queue 并都绑定订单事件，一条消息可能被处理 3 次，造成重复增加积分。

## 7. CloudMall 消息设计

```text
同步：库存扣减成功 + 创建订单成功
→ 发布 order.created
→ RabbitMQ topic Exchange
  ├─ order.points.queue：按 orderNo 幂等增加积分
  ├─ order.sms.queue：发送下单通知
  ├─ order.logistics.queue：初始化物流流程
  └─ order.audit.queue：绑定 order.#，记录订单事件
```

今天的重点是消息模型和消费幂等。数据库事务成功与消息可靠发送之间仍可能存在一致性问题，生产中需要进一步学习 Publisher Confirm、消息重试、死信队列和可靠事件投递设计。

## 9. 面试表达

### 为什么下单后要使用消息队列？

下单后的短信、积分、物流初始化和营销统计不直接决定订单是否创建成功，可以通过 RabbitMQ 异步处理。这样订单服务不需要同步等待下游服务，提升响应速度；新增消费者不需要修改订单核心流程，实现解耦；高峰流量先进入队列，消费者按能力处理，实现削峰。订单创建和库存扣减仍必须在同步核心链路中完成，消息队列不能替代库存原子扣减和订单幂等。

### Exchange、Binding、Routing Key 的关系是什么？

Producer 将带有 Routing Key 的消息发送给 Exchange；Exchange 根据 Binding 规则将消息路由到一个或多个 Queue。Exchange 是路由中心，Routing Key 是消息携带的路由标签，Binding 是 Exchange 到 Queue 的路由规则。Queue 负责存储消息，Consumer 从 Queue 消费消息。

### 为什么消息消费必须做幂等？

手动 ack 可以避免消费者在业务处理前异常造成消息丢失，但消费者处理成功后、ack 到达 Broker 前仍可能发生网络异常或宕机，Broker 会重新投递消息。消费者应使用 `orderNo`、事件 ID、消费记录或数据库唯一约束识别重复消息，确保积分、优惠券等业务只执行一次。
