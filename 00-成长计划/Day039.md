## 2. 锁的作用

多个事务同时操作互相影响的数据时，InnoDB 通过锁协调执行顺序，避免写写冲突和不符合业务预期的并发修改。

锁有两条理解主线：

```text
共享锁、排他锁：其他事务是否还能读或写
记录锁、间隙锁、临键锁：锁住索引的哪一部分
```

普通 `SELECT` 通常是 MVCC 快照读，读取可见版本，一般不需要在本节讨论的共享锁或排他锁。

---

## 3. 共享锁与排他锁

### 3.1 共享锁（S Lock）

共享锁允许多个事务同时读取同一数据，但阻止其他事务对该数据加排他锁修改。

```sql
SELECT *
FROM product_stock
WHERE product_id = 'P001'
FOR SHARE;
```

适用场景：事务内需要读取当前数据，并避免它在提交前被其他事务修改。

### 3.2 排他锁（X Lock）

排他锁允许当前事务读写数据，其他事务不能再对同一数据加共享锁或排他锁，只能等待当前事务提交或回滚。

```sql
UPDATE product_stock
SET stock = stock - 1
WHERE product_id = 'P001';

SELECT *
FROM product_stock
WHERE product_id = 'P001'
FOR UPDATE;
```

`UPDATE`、`DELETE` 和 `SELECT ... FOR UPDATE` 都会涉及排他锁。

### 3.3 兼容关系

| 已有锁 | 新增 S 锁 | 新增 X 锁 |
| --- | --- | --- |
| S 锁 | 可以 | 等待 |
| X 锁 | 等待 | 等待 |

商品详情页只展示库存时，应使用普通 `SELECT`。若每次展示都使用 `FOR UPDATE`，会额外持有排他锁，阻塞库存扣减等写操作，降低并发能力。

## 4. InnoDB 的锁范围

InnoDB 的行锁本质上加在**索引记录**上。假设索引中已有：

```text
P001    P003    P005
```

### 4.1 记录锁（Record Lock）

记录锁锁住一条已存在的索引记录。

```sql
SELECT *
FROM product_stock
WHERE product_id = 'P003'
FOR UPDATE;
```

若 `product_id` 是主键或唯一索引，查询精确命中 `P003` 时，重点锁住 `P003` 这一条记录。

```text
其他事务修改或删除 P003：等待
其他事务操作 P001、P005：通常不受影响
```

### 4.2 间隙锁（Gap Lock）

间隙锁锁住两条索引记录之间的空位，主要阻止其他事务向该范围插入新索引记录。

```text
间隙：(P001, P003)
```

锁住该间隙后，其他事务不能插入 `P002`，因为 `P002` 会落入这个索引范围。

间隙锁的主要目的：防止其他事务插入满足当前范围查询条件的新记录，从而避免幻读。

### 4.3 临键锁（Next-Key Lock）

临键锁可以理解为：**记录锁 + 该记录前的间隙锁**。

```text
(P001, P003]
```

含义：

- 间隙 `(P001, P003)` 被锁住，不能插入 `P002`。
- 记录 `P003` 被锁住，不能被其他事务修改或删除。

在 MySQL InnoDB 的可重复读隔离级别下，范围条件的当前读，例如 `FOR UPDATE`、`UPDATE`、`DELETE`，经常涉及间隙锁或临键锁，用来降低幻读风险。

```sql
SELECT *
FROM product_stock
WHERE product_id >= 'P003'
  AND product_id < 'P005'
FOR UPDATE;
```

实际锁定范围会受索引、唯一性、查询边界、隔离级别和执行计划影响，不能只靠 SQL 表面形式绝对判断。

## 5. 索引为什么会影响锁冲突

索引不仅提升查询性能，也能帮助数据库更精确地定位需要修改的记录，因此通常缩小锁范围、减少锁冲突。

```sql
-- 主键定位，范围通常较小
UPDATE product_stock
SET stock = stock - 1
WHERE product_id = 'P001';

-- 若 remark 无合适索引，可能扫描并影响更多记录
UPDATE orders
SET status = 'CANCELLED'
WHERE remark = '测试订单';
```

缺少合适索引时，数据库可能扫描更多索引记录和数据记录，锁冲突概率上升，严重时会明显拖慢并发事务。

边界：锁范围仍取决于实际执行计划、SQL 条件和隔离级别，应结合 `EXPLAIN` 与线上证据分析。

## 6. 锁等待

```text
事务 A：更新 P001，获得排他锁，但尚未提交
事务 B：更新 P001，需要获得同一条记录的排他锁
```

事务 B 通常会等待事务 A 提交或回滚。若等待超过数据库配置的超时时间，会出现锁等待超时。

锁会在事务**提交或回滚**时释放。因此应缩短事务：

- 事务内只保留必要且快速的数据库操作。
- 不在事务中调用耗时远程接口。
- 不在事务中进行文件处理、大量循环计算或等待用户操作。

长事务会导致锁持有时间变长，进一步造成请求等待、连接与线程堆积、接口变慢甚至锁等待超时。

## 7. 死锁

### 7.1 是什么

死锁是多个事务形成循环等待，彼此都持有对方需要的锁，因而无法继续执行。

```text
事务 A：先锁 P001，再等待 P002
事务 B：先锁 P002，再等待 P001
```

这与单纯的锁等待不同：锁等待可能在对方提交后自然结束；死锁形成循环，无法自行解除。

InnoDB 检测到死锁后，会主动回滚其中一个事务，让另一个事务继续执行。

### 7.2 如何降低死锁概率

- 多行、多表更新采用统一加锁顺序，例如都按 `product_id` 升序。
- 为高频更新 SQL 建立合适索引，缩小锁范围。
- 缩短事务，避免不必要的锁持有时间。
- 减少不必要的范围锁定和批量更新。
- 对确认可安全重试的死锁异常进行有限次数重试。

统一顺序示例：

```text
事务 A：先更新 product_stock，再更新 orders
事务 B：也先更新 product_stock，再更新 orders
```

重点不是“先库存还是先订单”本身，而是所有并发事务都遵守同一顺序，避免出现循环等待。

### 7.3 为什么是有限重试

死锁通常是瞬时并发冲突。数据库已回滚其中一个事务并释放锁，重试时可能不再发生相同竞争，因此可以重试。

但必须限制次数并适当退避，否则持续重试会放大数据库压力。重试前还要确认事务具备幂等性，避免数据库事务失败但外部支付、消息发送等副作用已经成功。

## 8. 线上排查顺序

```text
确认应用异常：Deadlock、SQLState 40001、事务被回滚
  ↓
获取数据库死锁日志
  ↓
还原等待链：谁持有什么锁、又等待什么锁
  ↓
定位对应 SQL、索引、事务执行顺序和耗时
  ↓
统一加锁顺序、优化索引、缩短事务、必要时有限重试
  ↓
验证并持续监控
```

MySQL 中可以使用：

```sql
SHOW ENGINE INNODB STATUS;
```

它通常只展示最近一次死锁信息；线上还应结合数据库日志、慢 SQL、应用链路和监控进行分析。

## 9. CloudMall：`FOR UPDATE` 与条件更新

### 9.1 单商品库存扣减

优先使用条件更新：

```sql
UPDATE product_stock
SET stock = stock - 1
WHERE product_id = ?
  AND stock > 0;
```

并检查受影响行数：

```text
1：扣减成功
0：库存不足或商品不存在
```

原因：

- 库存判断与扣减由一条 SQL 原子完成。
- 一次 SQL 往返，锁持有区间更短。
- 受影响行数可以直接表达扣减是否成功。
- 多个实例共用同一数据库时仍然有效，不依赖 JVM 内存锁。

### 9.2 何时使用 `SELECT ... FOR UPDATE`

当业务必须先读取多项当前数据，再依据这些数据做一组相关更新时，可以考虑悲观锁。

例如：读取优惠券状态与库存、计算用户积分、更新多条关联记录，并要求这些判断和更新在同一事务中基于当前数据完成。

`FOR UPDATE` 的代价是锁持有时间更长、冲突概率更高，因此不应用于普通商品详情读取，也不应作为简单单商品扣库存的默认方案。

### 9.3 当前 Demo 边界

Day038 的 H2 Demo 已验证条件更新：库存为 `1` 时第一次扣减成功、第二次失败。

H2 不等价于 MySQL InnoDB，不能用它验证间隙锁、临键锁、真实死锁日志或 MySQL 的锁等待表现。需要连接 MySQL 后，再用多会话事务和 InnoDB 日志做进一步验证。

## 10. 面试表达

### 索引为什么能减少锁冲突？

索引除了加快查询，还能帮助 InnoDB 更精确地定位需要操作的索引记录，因此通常缩小锁范围、减少锁冲突。没有合适索引时，更新可能扫描和影响更多记录。CloudMall 按主键 `product_id` 更新单个商品库存，比按无索引的备注字段批量更新，锁影响范围通常更小。但最终仍要结合 `EXPLAIN` 确认实际执行计划。

### 什么是死锁，如何降低死锁概率？

死锁是多个事务形成循环等待，例如事务 A 持有 P001 等待 P002，事务 B 持有 P002 等待 P001。InnoDB 会检测后回滚其中一个事务。工程上我会统一多行多表的加锁顺序、让 SQL 命中合适索引、缩短事务，并对幂等的数据库操作做有限重试。线上再通过死锁日志和对应 SQL 还原等待链，定位根因。

### 为什么单商品扣库存优先使用条件更新？

我会使用 `UPDATE ... SET stock = stock - 1 WHERE product_id = ? AND stock > 0`，检查受影响行数。判断库存与扣减库存由一条 SQL 原子完成，只需一次数据库交互，锁持有时间更短。`SELECT ... FOR UPDATE` 更适合必须读取多项当前数据后再做一组相关更新的复杂事务。
