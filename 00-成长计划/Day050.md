## 2. 单体与微服务

### 2.1 单体架构

单体应用将多个业务模块部署在同一个进程中：

```text
CloudMall
  ├─ 商品模块
  ├─ 订单模块
  ├─ 库存模块
  └─ 积分模块
```

模块间通常是本地方法调用：

```java
stockService.deduct(productId, quantity);
```

优点：

```text
开发和部署简单
本地调用速度快
本地事务容易管理
适合早期或中小规模系统
```

问题会在模块和流量增长后出现：

```text
订单流量变大
-> 整个应用都要一起扩容

库存模块发布修复
-> 整个应用都要一起发布

模块代码互相依赖增多
-> 修改一个模块更容易影响其他模块
```

### 2.2 微服务架构

微服务按业务边界拆分为可独立开发、部署和扩缩容的服务：

```text
商品服务：商品详情、分类、价格
订单服务：创建订单、订单状态
库存服务：可售库存、锁定库存
积分服务：积分增加与查询
```

收益：

```text
订单流量大 -> 只扩容订单服务
库存服务发版 -> 只发布库存服务
积分业务变慢 -> 可异步处理，不阻塞订单核心链路
```

代价：

```text
本地调用变成网络调用
服务地址需要动态管理
远程调用会超时、失败或重复
多服务日志、配置、监控更复杂
跨服务一致性不能只依赖本地数据库事务
```

微服务不是“拆得越多越好”。当前 CloudMall 是单体 Demo，尚未实际拆分；是否拆分应结合团队边界、独立部署需求、流量差异和运维能力决定。

## 3. Spring Cloud 解决什么问题

Spring Cloud 提供微服务常见问题的抽象和组件生态：

| 能力 | 解决的问题 | CloudMall 场景 |
| --- | --- | --- |
| 注册中心 | 服务地址动态变化，调用方不能写死 IP | 订单服务查找库存服务实例 |
| 配置中心 | 多服务配置统一管理和动态更新 | 数据库、Redis、消息队列配置管理 |
| 服务调用 | 用服务名调用远程服务 | `order-service` 调用 `stock-service` |
| 负载均衡 | 多个健康实例之间分配请求 | 多个库存实例分担扣减请求 |
| 网关 | 对外统一入口、路由、鉴权、限流 | 前端统一访问 API 网关 |
| 熔断与降级 | 防止下游故障扩散 | 商品详情查询失败时返回兜底信息 |

```text
服务注册
-> 服务发现
-> 客户端负载均衡
-> 服务调用
-> 超时、熔断、降级与监控
```

Spring Cloud 提供服务发现和负载均衡等通用抽象，具体实现可以是 Eureka、Consul 等注册中心实现；在后续学习中计划使用 Nacos 作为注册和配置中心。[Spring Cloud Commons](https://docs.spring.io/spring-cloud-commons/reference/spring-cloud-commons/common-abstractions.html)

## 4. 注册中心与服务发现

### 4.1 为什么不能写死地址

库存服务可能部署多个实例：

```text
10.0.0.1:8081
10.0.0.2:8081
10.0.0.3:8081
```

服务实例会因为扩容、发布、容器重建、故障和下线而变化。若订单服务把地址直接写在配置文件中：

```text
新增、下线或更换库存实例
-> 需要人工修改订单服务配置
-> 可能需要重启或重新发布调用方
-> 服务越多，配置维护关系越复杂
```

注册中心统一维护服务实例信息，调用方只依赖服务名，不依赖固定 IP 和端口。

### 4.2 注册、心跳、发现和下线

```text
库存服务启动
-> 向注册中心登记 stock-service 与实例地址
-> 周期性发送心跳

订单服务调用库存服务
-> 按 stock-service 查询健康实例列表
-> 负载均衡选择一个实例
-> 发起远程调用

库存服务停止或长期未发送心跳
-> 注册中心标记不健康或移除实例
-> 后续调用不再选择该实例
```

一条实例注册信息通常包括：

| 信息 | 示例 | 作用 |
| --- | --- | --- |
| 服务名 | `stock-service` | 调用方查找服务的逻辑名称 |
| 地址 | `10.0.0.1:8081` | 实际网络访问位置 |
| 健康状态 | `UP`、`DOWN` | 避免调用故障实例 |
| 最后心跳时间 | 最近一次上报时间 | 判断实例是否失联 |
| 元数据 | 版本、区域、权重、标签 | 灰度、就近访问或路由策略的依据 |

心跳机制解决的是“实例宕机后不能长时间被当作可用实例”的问题。

### 4.3 DiscoveryClient

`DiscoveryClient` 是 Spring Cloud 的服务发现抽象。调用方按服务名获得服务实例列表，再由负载均衡组件选择实际地址。

现代 Spring Cloud 中，引入对应的服务发现客户端实现后即可触发注册发现能力，通常不需要再显式添加 `@EnableDiscoveryClient`。[Spring Cloud Commons](https://docs.spring.io/spring-cloud-commons/reference/spring-cloud-commons/common-abstractions.html)

本机未引入或运行 Nacos 客户端，本节只完成原理学习，不代表 CloudMall 已完成服务注册发现。

## 5. 客户端负载均衡

订单服务发现库存服务的健康实例后，仍需要选择一个具体实例：

```text
stock-service
  ├─ 10.0.0.1:8081  UP
  ├─ 10.0.0.2:8081  UP
  └─ 10.0.0.3:8081  DOWN
```

不能固定调用第一个实例：

```text
10.0.0.1 承受全部请求
10.0.0.2 长期空闲
10.0.0.1 故障后，即使其他实例健康也会调用失败
```

客户端负载均衡从健康实例列表中选取一个目标：

| 策略 | 含义 | 适用说明 |
| --- | --- | --- |
| 轮询 | A -> B -> A -> B | 实例性能接近时的基础策略 |
| 随机 | 随机选择健康实例 | 实现简单，长期分布通常较均匀 |
| 加权 | 性能更强实例获得更多请求 | 实例容量不同的场景 |

在 Spring Cloud 中，`@LoadBalanced` 可以让客户端使用服务名而不是固定地址：

```text
http://stock-service/api/stocks/P001
```

负载均衡组件会将服务名解析为一个实际健康实例地址。Spring Cloud 官方文档也说明，负载均衡客户端使用虚拟主机名（服务名）而不是物理主机地址。[Spring Cloud Commons](https://docs.spring.io/spring-cloud-commons/reference/spring-cloud-commons/common-abstractions.html)

## 6. 远程调用的超时、重试、熔断和降级

拆分后，订单服务调用库存服务不再是本地方法调用，而是网络调用：

```text
订单服务
-> 查找 stock-service 健康实例
-> 选择一个实例
-> 发起网络请求
-> 处理成功、超时、异常与补偿
```

### 6.1 超时

超时用于避免调用方无限等待响应缓慢、网络异常或已宕机的服务。

```text
没有超时
-> 请求线程长期阻塞
-> 线程池耗尽
-> 故障扩散到订单服务
```

### 6.2 重试

重试适合网络瞬时抖动等临时失败，但必须谨慎：

```text
查询商品详情失败
-> 可以尝试有限次重试

库存扣减失败
-> 不应在没有幂等保障时盲目重试
-> 否则可能重复扣减库存
```

写操作重试前，需要有幂等键、请求唯一标识、条件更新或其他防重复机制。

### 6.3 熔断

当对某个下游服务的调用持续失败时，熔断机制可以在一段时间内快速失败，暂时停止继续向故障服务发送大量请求，防止雪崩。

```text
库存服务持续超时
-> 订单服务不再持续堆积等待请求
-> 快速返回失败或进入受控补偿流程
```

熔断通常针对持续失败的服务调用，而不仅是某一个单独实例；负载均衡会先尝试选择其他健康实例。

### 6.4 降级

降级是在下游不可用时提供有限能力或可理解结果：

```text
商品详情查询失败
-> 可展示基础商品信息并提示库存暂不可用

库存扣减失败
-> 不能伪造下单成功
-> 应返回下单失败或处理中，并配合幂等、补偿和对账
```

核心写操作与非核心查询的降级策略不同。库存扣减、支付和订单创建等核心状态不能通过“返回成功”来降级。

## 9. 面试表达

### 9.1 为什么微服务需要注册中心？

> 微服务环境中，服务实例会随着扩容、发布、容器重建和故障发生动态变化，调用方不能依赖写死的 IP 和端口。注册中心统一维护服务名、实例地址、健康状态和心跳信息；调用方通过服务名发现健康实例，从而减少人工维护地址的成本，也能及时避开下线或故障实例。

### 9.2 服务注册发现的基本流程是什么？

> 服务启动时向注册中心注册自己的服务名和实例地址，并通过心跳维持健康状态。调用方按服务名从注册中心获取健康实例列表，再交给负载均衡组件选择一个真实地址发起调用。实例停止或长期无心跳时，注册中心会将其标记不健康或移除，后续调用不再选择该实例。

### 9.3 为什么还需要超时、熔断和降级？

> 服务发现和负载均衡只能帮助我找到健康实例，但网络抖动、下游变慢和服务故障仍可能让调用失败。超时防止调用方无限等待；熔断在持续失败时快速失败，避免请求和线程持续堆积；降级保证非核心查询在部分故障时仍能提供有限能力。对于库存扣减等核心写操作，不能降级为成功，也不能在无幂等保障时盲目重试，需要结合条件更新、幂等和补偿保证正确性。
