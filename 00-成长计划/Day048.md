## 2. 可靠性不是一个开关

订单事件从创建到积分服务处理成功，至少经过四段链路：

```text
订单服务
  -> RabbitMQ Broker
  -> 目标 Queue
  -> 积分消费者
  -> 积分数据库
```

不同机制解决不同的问题：

| 机制 | 解决的问题 | 不解决的问题 |
| --- | --- | --- |
| Publisher Confirm | Producer 发送的消息是否到达 Broker | Queue 是否匹配、Consumer 是否成功处理 |
| Return 回调 | 到达 Exchange 的消息是否无法路由到 Queue | Broker 是否已接收、Consumer 是否成功处理 |
| Exchange、Queue、消息持久化 | Broker 重启后元数据与消息尽量保留 | Consumer 的业务执行结果 |
| 手动 `ack` | Consumer 成功处理前异常时，Broker 可以重新投递 | 重复投递导致的重复业务 |
| 幂等消费 | 重复消息不会重复执行业务 | 消息是否成功到达 Broker |

```text
Confirm：Producer -> Broker
Return：Exchange -> Queue
持久化：Broker 重启后的消息保留
ack：Consumer 是否成功处理
幂等：重复消息的业务效果只执行一次
```

## 3. Publisher Confirm 与 Return

### 3.1 Publisher Confirm

Publisher Confirm 是 Broker 给 Producer 的确认机制。

```text
订单服务发送 order.created
-> RabbitMQ Broker 接收消息
-> Broker 返回 Confirm
```

它回答的是：

> 订单服务尝试发送消息后，RabbitMQ Broker 是否已经接收？

CloudMall 下单后发送 `order.created` 时，若 Broker 不可用、连接中断或消息没有成功抵达 Broker，Producer 可以通过 Confirm 失败结果记录异常，并由本地消息表后续重试。

Confirm 成功不代表：

```text
不代表消息已经路由到 Queue
不代表积分服务已经消费
不代表积分已经写入数据库
```

### 3.2 Return 回调

Return 处理的是消息已经到达 Exchange，但没有任何 Queue 匹配的情况。

```text
Exchange：order.event.topic
Routing Key：order.create
Binding：order.created -> order.points.queue
```

上例中 `order.create` 与 `order.created` 不匹配。Broker 可能已经接收消息，但消息无法路由到积分队列。生产端开启 `mandatory` 和 Return 回调后，可以发现这类路由配置或 Routing Key 错误。

```text
Confirm：确认到达 Broker
Return：发现无法路由到 Queue
```

## 4. RabbitMQ 重启后的消息保留

Confirm 与 Return 都不能解决 Broker 重启后的消息丢失问题。需要配合：

```text
持久化 Exchange
+ 持久化 Queue
+ 消息持久化
```

三者缺一不可。例如 Queue 是持久化的，但发送的是非持久化消息，Broker 异常重启后该消息仍可能丢失。

持久化提升消息保留能力，但不等于端到端绝不丢消息：应用发送前宕机、消费者执行失败、重复投递等问题仍需要本地消息表、手动确认、重试和幂等处理。

## 5. 手动 ack、失败分类与幂等

### 5.1 手动 ack

积分服务的正确顺序：

```text
收到 order.created
-> 校验消息
-> 写入消费记录并增加积分
-> 本地数据库事务提交成功
-> Consumer 发送 ack
-> Broker 删除消息
```

如果数据库连接失败或事务回滚，不能 `ack`，否则 Broker 会认为消息已处理并删除它，积分业务会丢失。

### 5.2 为什么仍会重复消费

```text
1. 积分服务已成功增加积分
2. ack 到达 Broker 前，应用宕机或网络中断
3. Broker 没有收到 ack，重新投递消息
4. 积分服务再次收到同一个消息
```

因此 RabbitMQ 的实际语义通常是“至少投递一次”，而不是自动的“恰好一次”。

### 5.3 幂等消费

消费者可以使用 `messageId` 或 `orderNo` 去重：

```text
messageId：标识某一条具体事件，例如 M001
orderNo：适合一个订单只能增加一次积分的业务约束
```

常见实现是在一个本地数据库事务中：

```text
1. 插入 messageId 消费记录
2. 消费记录唯一索引冲突：说明已经处理，直接 ack
3. 插入成功：增加积分
4. 事务提交成功后 ack
```

这样同一消息被重复投递时，积分不会重复增加。

## 6. 重试队列与死信队列

### 6.1 为什么不能无限 requeue

数据库短暂不可用时，立即 `requeue=true` 可能使消息被迅速重新投递：

```text
消费失败
-> 立即回到原队列
-> 再次消费
-> 再次失败
-> 高频循环
```

这会消耗消费者线程、CPU、网络和数据库连接，放大故障，并让失败消息持续积压。

### 6.2 异常分类

| 异常类型 | 示例 | 处理方式 |
| --- | --- | --- |
| 临时性异常 | 数据库短暂不可用、下游超时 | 延迟重试，限制次数 |
| 永久性异常 | `userId` 不存在、消息格式错误、业务状态非法 | 进入死信队列，告警与人工补偿 |

### 6.3 队列流转

```text
order.points.queue
  -> 临时失败
order.points.retry.30s.queue
  -> 等待 30 秒，TTL 到期
死信交换机
  -> 重新路由
order.points.queue
  -> 达到最大重试次数或永久性异常
order.points.dlq
```

重试队列通过 TTL 暂存消息；消息过期后经死信交换机回到业务队列，再次尝试消费。达到最大重试次数后进入最终死信队列，不再无限自动重试。

`nack/reject` 且 `requeue=false`、消息 TTL 到期等情况可以触发死信路由。死信队列不是垃圾桶，必须监控积压、配置告警，并制定人工修复或补偿流程。

## 7. 本地消息表（Outbox）解决什么问题

只使用 Confirm 仍有一个缺口：

```text
订单数据库事务提交成功
-> 应用还未来得及发送 order.created
-> 应用宕机
-> RabbitMQ 没有任何消息
-> 积分、短信、物流都不会触发
```

因为应用没有执行发送动作，所以不会产生 Confirm 结果。解决方案是本地消息表。

### 7.1 同一事务写订单与消息表

```text
一个本地数据库事务内：

1. 创建订单
2. 插入本地消息表，状态为 PENDING
3. 一起提交
```

示例字段：

| 字段 | 含义 |
| --- | --- |
| `message_id` | 事件唯一标识，例如 M001 |
| `order_no` | 关联订单号，例如 O001 |
| `event_type` | 事件类型，例如 `order.created` |
| `payload` | 事件内容 |
| `status` | `PENDING`、`SENT`、`FAILED` 等状态 |
| `retry_count` | 已发送重试次数 |

必须在同一事务的原因：

```text
订单成功、消息表失败
-> 订单存在，但下游永远收不到事件

消息表成功、订单失败
-> 下游可能处理一笔不存在的订单
```

同一事务保证：

```text
订单存在，且一定存在一条待投递消息
或
订单不存在，且不会存在待投递消息
```

### 7.2 后续投递与补偿

```text
定时任务扫描 PENDING 消息
-> 发送到 RabbitMQ
-> Confirm 成功
-> 更新消息状态为 SENT

发送失败
-> 保持 PENDING 或记录 FAILED
-> 增加 retry_count
-> 后续重试、告警或人工处理
```

若 Broker 已经收到消息，但应用在更新 `SENT` 前宕机，恢复后可能再次发送同一条消息。因此本地消息表降低丢失风险，但会带来重复投递可能；消费者幂等是不可省略的配套措施。

## 8. CloudMall 可靠消息方案

```text
同步核心链路

库存扣减成功
-> 创建订单
-> 写入 order.created 本地消息表
-> 订单与消息表同一事务提交

异步投递链路

扫描 PENDING 消息
-> 发送 order.created 到 RabbitMQ
-> Confirm 成功后标记 SENT
-> Return 发现路由失败后告警与重试

消费链路

积分服务收到消息
-> 通过 messageId 或 orderNo 判断是否已处理
-> 消费记录与增加积分同一事务提交
-> 成功后手动 ack
-> 临时失败延迟重试
-> 最终失败进入死信队列
```

边界：

- 本地消息表、Confirm 和幂等实现的是最终一致性，不是让订单、RabbitMQ、积分数据库形成一个全局强事务。
- 库存扣减和订单创建仍属于同步核心链路，需要使用数据库条件更新、Redis Lua 等方案保证正确性。
- 本机未启动 RabbitMQ，因此本日没有实际验证 Confirm、Return、重试或死信队列行为。

## 9. 面试表达

### 9.1 如何保证 RabbitMQ 消息尽量不丢？

> 我会分链路处理。生产端使用 Publisher Confirm 确认消息到达 Broker，使用 Return 回调发现消息无法路由到 Queue，并配置 Exchange、Queue 和消息持久化。消费者使用手动 ack，在本地业务事务成功后再确认消息。对于订单创建与消息发送之间的空档，我会把订单和本地消息表放在同一个数据库事务中，再由任务扫描待发送消息并重试投递。最后，消费者必须幂等，因为重试和网络异常都可能产生重复消息。

### 9.2 为什么消息队列仍需要幂等消费？

> 手动 ack 能降低消费者处理前宕机导致的消息丢失，但业务操作成功后、ack 到达 Broker 前仍可能发生异常，Broker 会重新投递。因此消费者通常至少会收到一次消息，需要通过 `messageId`、`orderNo`、消费记录表和唯一约束防止积分、优惠券等业务重复执行。

### 9.3 重试和死信队列如何选择？

> 我会先区分异常是否可恢复。数据库短暂不可用、下游超时等临时异常，使用带间隔和次数上限的延迟重试；参数非法、用户不存在等永久异常不应无限重试，应进入死信队列，保留现场、告警并进行人工补偿。无限立即重试会放大故障，挤占消费者和数据库资源。
