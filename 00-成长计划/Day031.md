## 2. IoC 与 DI

### 2.1 IoC 是什么

IoC（Inversion of Control，控制反转）指对象不再由业务代码主动 `new` 创建，而是交给 Spring 容器创建、保存和管理。

传统方式中，`ProductService` 自己创建 `ProductRepository`；使用 IoC 后，Spring 创建两者，并负责建立依赖关系。

### 2.2 为什么需要 IoC

- 业务类不再直接依赖具体对象的创建过程，降低耦合。
- 更容易替换实现，例如把内存商品仓库替换为数据库商品仓库。
- Spring 统一管理对象生命周期和配置。

### 2.3 DI 是什么

DI（Dependency Injection，依赖注入）是 Spring 实现 IoC 的具体方式。

例如 `ProductService` 依赖 `ProductRepository`，Spring 创建 `ProductRepository` 后，通过构造器传入 `ProductService`。

```java
@Service
public class ProductService {

    private final ProductRepository productRepository;

    public ProductService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }
}
```

### 2.4 IoC 与 DI 的关系

- IoC 是思想：对象交给容器管理。
- DI 是实现方式：容器把依赖对象注入目标对象。
- 可以理解为：IoC 说明“谁负责管理对象”，DI 说明“依赖如何交给对象”。

## 3. Bean 与组件扫描

### 3.1 Bean 是什么

Bean 是由 Spring 容器创建和管理的对象。

不是所有 `new` 出来的对象都是 Bean。只有被 Spring 识别并注册到容器中的对象才是 Bean。

### 3.2 常见组件注解

| 注解 | 常见职责 |
| --- | --- |
| `@Component` | 通用组件 |
| `@Service` | 业务层服务 |
| `@Repository` | 数据访问层 |
| `@Controller` / `@RestController` | Web 控制层 |

这些注解都能让类被 Spring 扫描并注册为 Bean，区别主要是语义表达。

### 3.3 组件扫描规则

`@SpringBootApplication` 包含组件扫描能力，默认扫描启动类所在包及其子包。

CloudMall 的启动类位于：

```text
com.cloudmall.CloudMallApplication
```

因此位于以下包中的类可以被扫描：

```text
com.cloudmall.demo.spring
```

如果业务类放在 `com.cloudmall` 之外，默认不会被扫描，需要调整包结构或显式配置扫描范围。

### 3.4 `@Bean` 的使用场景

对于自己无法直接修改源码的第三方类，或需要复杂创建逻辑的对象，可以在配置类中通过 `@Bean` 注册。

```java
@Bean
public XxxClient xxxClient() {
    return new XxxClient();
}
```

## 4. 依赖注入方式与作用域

### 4.1 三种注入方式

| 方式 | 特点 | 建议 |
| --- | --- | --- |
| 构造器注入 | 依赖不可缺少，字段可使用 `final` | 优先使用 |
| Setter 注入 | 适合可选依赖 | 按需使用 |
| 字段注入 | 写法短，但不利于测试和不可变设计 | 不推荐作为生产代码默认方式 |

单构造器场景下，即使不写 `@Autowired`，Spring 也会自动进行构造器注入。

### 4.2 常见作用域

| 作用域 | 含义 | 典型场景 |
| --- | --- | --- |
| `singleton` | 一个 Spring 容器中通常只有一个实例，默认作用域 | 无状态 Service、Repository |
| `prototype` | 每次获取 Bean 都创建新实例 | 有临时状态的对象 |
| `request` | 每个 HTTP 请求一个实例 | 请求上下文对象 |
| `session` | 每个 HTTP Session 一个实例 | 会话级状态 |

注意：`singleton` 是“一个 Spring 容器一个实例”，不是整个分布式系统只有一个实例，也不代表该对象天然线程安全。

## 5. CloudMall Demo

### 5.1 Bean 依赖关系

```text
ProductRepository
        ↓
ProductService
        ↓
CommandLineRunner
```

- `ProductRepository` 负责模拟根据商品 ID 查询商品。
- `ProductService` 通过构造器注入 `ProductRepository`。
- 启动类使用 `CommandLineRunner` 注入 `ProductService` 并调用查询方法。
- 全部对象由 Spring 容器创建和管理，不在业务代码中手动 `new`。

### 5.2 启动类验证方式

```java
@Bean
CommandLineRunner productDemoRunner(ProductService productService) {
    return args -> {
        System.out.println(productService.getProduct("P001"));
    };
}
```

预期输出：

```text
P001商品
```

## 6. 面试表达

### 6.1 什么是 IoC 和 DI？

IoC 是把对象的创建和管理从业务代码转交给 Spring 容器；DI 是 Spring 实现 IoC 的方式，即容器在创建对象时，把它依赖的对象注入进去。

例如 CloudMall 的 `ProductService` 依赖 `ProductRepository`，我不在 `ProductService` 中手动创建仓库对象，而是由 Spring 创建 `ProductRepository` 后，通过构造器注入给 `ProductService`。这样业务层不依赖对象的具体创建过程，更容易替换实现和测试。

### 6.2 为什么优先使用构造器注入？

构造器注入可以明确对象创建时必须具备哪些依赖，依赖字段可以使用 `final`，避免对象创建后依赖被修改；同时单元测试中可以直接传入模拟对象，代码更容易测试。

### 6.3 Spring Boot 为什么能扫描到你的 Bean？

启动类位于 `com.cloudmall` 包下，`@SpringBootApplication` 默认扫描该包及其子包。`ProductService` 和 `ProductRepository` 位于 `com.cloudmall.demo.spring`，因此会被扫描并注册为 Bean。
