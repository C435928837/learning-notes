## 2. Redis 为什么需要持久化

Redis 的数据主要保存在内存中。进程崩溃、机器重启或故障切换时，内存数据可能丢失。持久化将内存中的数据保存到磁盘，使 Redis 重启后能够恢复。

持久化只能降低数据丢失风险，不能让 Redis 成为订单、库存的唯一事实来源。订单、支付和库存等核心状态仍应以数据库及对应的一致性方案为准。

## 3. RDB 与 AOF

### 3.1 RDB：内存快照

RDB 在某个时间点将 Redis 内存中的数据写入快照文件，例如 `dump.rdb`。

```text
10:00：生成 RDB 快照
10:05：Redis 宕机
重启后：最多只能恢复到接近 10:00 的数据
```

Redis 可按配置的时间和写入次数自动生成快照，也可手动触发 `BGSAVE`。执行后台保存时，Redis 通常由子进程写入快照，主进程继续处理请求；写入期间的数据修改会通过写时复制机制处理。

RDB 特点：

| 优点 | 边界 |
| --- | --- |
| 文件通常较紧凑，适合备份 | 两次快照之间的数据可能丢失 |
| 重启恢复通常较快 | 快照有 CPU、磁盘和内存压力 |

若只开启 RDB 且每 5 分钟生成一次快照，Redis 刚完成一次快照后到下一次快照前宕机，最多可能丢失接近 5 分钟的数据。

### 3.2 AOF：追加写命令

AOF 会将写命令追加记录到文件中：

```text
SET product:view-count:P001 100
INCR product:view-count:P001
HSET product:admin:P001 price 319.00
```

Redis 重启时通过重放 AOF 中的写命令恢复数据。

常见配置：

```text
appendonly yes
appendfsync everysec
```

| AOF 刷盘策略 | 含义 | 取舍 |
| --- | --- | --- |
| `always` | 每次写命令都尝试刷盘 | 数据更安全，性能开销较大 |
| `everysec` | 大约每秒刷盘一次 | 性能与数据安全的常见折中，极端故障可能丢失约 1 秒数据 |
| `no` | 由操作系统决定刷盘时机 | 性能较高，数据丢失窗口较大 |

AOF 通常比 RDB 文件大、恢复更慢。Redis 会通过 AOF 重写合并冗余写命令，减小文件体积：

```text
INCR product:view-count:P001
INCR product:view-count:P001
INCR product:view-count:P001
```

重写后可接近为：

```text
SET product:view-count:P001 3
```

### 3.3 对比与生产取舍

| 维度 | RDB | AOF |
| --- | --- | --- |
| 保存内容 | 某一时刻的全量数据快照 | 写命令日志 |
| 数据丢失窗口 | 取决于快照间隔，可能较大 | 通常较小，例如 `everysec` 约 1 秒 |
| 文件体积 | 通常较小 | 通常较大 |
| 恢复速度 | 通常较快 | 通常较慢 |
| 典型用途 | 备份、快速恢复 | 降低故障时的数据丢失窗口 |

生产中可同时开启 RDB 和 AOF：RDB 用于备份与较快恢复，AOF 用于降低数据丢失窗口。若 AOF 已启用，Redis 重启时通常优先使用 AOF 恢复，因为它通常包含更新的数据。

## 4. 过期删除

设置 TTL 的常见方式：

```redis
SETEX product:detail:P001 1800 '{"productCode":"P001"}'
EXPIRE product:detail:P001 1800
```

```text
TTL 到期：业务上该 Key 已失效
物理删除：不一定恰好在 TTL 到期瞬间完成
```

### 4.1 惰性删除

访问某个 Key 时，Redis 检查 TTL。若发现 Key 已过期，就删除并返回未命中。

```text
10:30：商品缓存 TTL 到期，但没有请求访问
10:35：请求读取该 Key
      -> Redis 发现已过期
      -> 删除 Key，返回未命中
```

优点：不需要在每个 Key 到期时都立即扫描删除，节省 CPU。  
边界：长期不被访问的过期 Key 可能暂时仍占用内存。

### 4.2 定期删除

Redis 会周期性抽样检查设置了 TTL 的 Key，并删除其中已过期的 Key。

优点：清理长期未访问的过期 Key，避免持续占用内存。  
边界：采用抽样而非一次全量扫描，以控制 CPU 消耗。

结论：惰性删除降低 CPU 扫描成本，定期删除防止未访问的过期 Key 长期占用内存，两者配合平衡性能与内存回收。

## 5. 内存淘汰

### 5.1 与过期删除的区别

| 概念 | 触发条件 | 处理对象 |
| --- | --- | --- |
| 过期删除 | Key 的 TTL 已到期 | 已过期 Key |
| 内存淘汰 | Redis 达到 `maxmemory`，新写入还需要内存 | 由 `maxmemory-policy` 决定的 Key，或拒绝写入 |

内存淘汰不是 Key 自己到期，而是 Redis 为新写入腾出空间的容量保护机制。

### 5.2 常见淘汰策略

| 策略 | 行为 | 适用思路 |
| --- | --- | --- |
| `noeviction` | 不删除 Key，拒绝后续需要更多内存的写入 | 不能接受 Redis 静默删数据，且有严格容量治理 |
| `allkeys-lru` | 从所有 Key 中淘汰最近最少使用的数据 | 缓存专用实例，访问时间局部性明显 |
| `allkeys-lfu` | 从所有 Key 中淘汰访问频率最低的数据 | 缓存专用实例，热点数据明显 |
| `volatile-lru` | 只从设置 TTL 的 Key 中淘汰最近最少使用的数据 | 只有部分 Key 允许被淘汰 |
| `volatile-lfu` | 只从设置 TTL 的 Key 中淘汰访问频率最低的数据 | 只有部分 Key 允许被淘汰且有热点特征 |
| `volatile-ttl` | 只从设置 TTL 的 Key 中优先淘汰更快到期的数据 | 希望优先释放即将失效缓存 |

`allkeys` 表示所有 Key 都可能被淘汰；`volatile` 表示只有设置 TTL 的 Key 才可能被淘汰。淘汰策略是 Redis 实例级配置，不是单个 Key 的配置。

## 6. CloudMall 商品缓存的容量治理

若 Redis 实例专门存放商品详情、首页推荐等可重建缓存，可考虑以下设计：

```text
持久化：AOF everysec + RDB 定期快照
商品详情 TTL：基础 TTL + 随机值
淘汰策略：allkeys-lfu
```

### 6.1 TTL 加随机值

```text
基础 TTL：30 分钟
随机值：0 到 5 分钟
最终 TTL：30 到 35 分钟
```

目的：让大量缓存分散过期，降低缓存雪崩和集中回源数据库的风险。

### 6.2 为什么缓存专用实例可选择 allkeys-lfu

热门商品访问频率通常更高。内存不足时，`allkeys-lfu` 倾向淘汰低频商品缓存，尽量保留热门缓存，减少热点请求回源数据库的概率。

`allkeys-lfu` 只判断访问频率，不判断业务重要性。因此不能将商品缓存与“绝不能丢失”的订单核心数据随意放在同一个实例：低频订单 Key 也可能被淘汰。

```text
商品详情缓存：允许淘汰，淘汰后可从数据库重建
订单、库存核心状态：不能只存在 Redis，必须以数据库等持久化存储为准
```

缓存与核心数据应进行实例或资源隔离；仅使用不同 Key 前缀不能隔离同一个实例的内存压力和淘汰策略。

### 6.3 监控与排查

| 指标 | 含义 | 异常后的排查方向 |
| --- | --- | --- |
| `used_memory` | 已使用内存 | 是否接近 `maxmemory`，是否出现大 Key 或写入增长 |
| `evicted_keys` | 因内存不足被淘汰的 Key 数 | 容量、策略、低价值 Key、Key/Value 大小 |
| `expired_keys` | 因 TTL 过期删除的 Key 数 | TTL 是否过短或是否集中到期 |
| `keyspace_hits` | 缓存命中次数 | 与业务流量一起观察缓存效果 |
| `keyspace_misses` | 缓存未命中次数 | 缓存失效、淘汰、击穿、Redis 故障或读写逻辑 |

若 `evicted_keys` 持续增长且 `keyspace_misses` 明显升高，通常说明内存不足导致缓存被淘汰，数据库回源压力可能随之增加。建议按以下顺序排查：

```text
1. Redis 可用性、连接错误率和延迟是否异常。
2. used_memory 是否接近 maxmemory，淘汰策略是否符合实例用途。
3. 是否出现大 Key、Value 过大、写入量突增或大量低价值 Key。
4. TTL 是否过短、大量 Key 是否同时过期、是否发生热点 Key 击穿。
5. 缓存 Key 设计、序列化、读写和删除逻辑是否有问题。
```

## 8. 面试表达

### RDB 和 AOF 有什么区别？

RDB 是某个时刻的全量内存快照，文件紧凑、恢复通常较快，但两次快照之间的数据可能丢失；AOF 记录写命令，使用 `everysec` 时通常最多丢失约 1 秒数据，但文件更大、恢复通常更慢。生产中可同时开启 RDB 和 AOF，使用 RDB 做备份和较快恢复，使用 AOF 缩小故障时的数据丢失窗口。核心订单和库存仍应以数据库为准，不能只依赖 Redis 持久化。

### Redis Key 到期后会立即从内存删除吗？

不一定。Redis 使用惰性删除和定期删除：访问 Key 时发现过期就删除，后台也会周期性抽样清理过期 Key。这样既避免频繁全量扫描消耗 CPU，也避免长期未访问的过期 Key 持续占用内存。

### Redis 内存满了如何处理商品详情缓存？

先区分过期删除与内存淘汰。达到 `maxmemory` 后，Redis 按实例级淘汰策略处理 Key。对于专门存放商品详情缓存的实例，可根据热点特征选择 `allkeys-lfu`，让低频缓存优先淘汰；商品详情设置带随机值的 TTL，避免集中失效。订单和库存等核心数据不应与可淘汰缓存混放，也不能只存在 Redis。
