## 2. CloudMall 核心表拆分

```text
products (1)
   │
   ├── product_stock (1)
   │
   └── orders (N)
```

| 表 | 主要职责 | 拆分原因 |
| --- | --- | --- |
| `products` | 商品编码、名称、当前售价等基础信息 | 商品展示与维护频率高 |
| `product_stock` | 可售库存、锁定库存等高并发库存数据 | 库存扣减与商品编辑的读写模式不同 |
| `orders` | 用户购买行为、订单状态、成交商品快照 | 订单持续增长，查询与商品表不同 |

当前 Demo 的简化表结构：

```sql
CREATE TABLE products (
    product_code VARCHAR(20) PRIMARY KEY,
    product_name VARCHAR(50) NOT NULL,
    price DECIMAL(10, 2) NOT NULL
);

CREATE TABLE product_stock (
    product_id VARCHAR(20) PRIMARY KEY,
    available_stock INT NOT NULL,
    locked_stock INT NOT NULL DEFAULT 0
);

CREATE TABLE orders (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    order_no VARCHAR(32) NOT NULL UNIQUE,
    user_id BIGINT NOT NULL,
    product_id VARCHAR(20) NOT NULL,
    product_name VARCHAR(50) NOT NULL,
    product_price DECIMAL(10, 2) NOT NULL,
    quantity INT NOT NULL,
    total_amount DECIMAL(10, 2) NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

金额字段使用数据库 `DECIMAL`，Java 中使用 `BigDecimal`，避免 `double`、`float` 的精度误差。

## 3. 为什么订单要保存商品快照

订单不能只保存 `product_id`，还需要保存下单时的商品名称、成交单价等快照。

```text
下单时：机械键盘，299 元
之后：商家改名为“机械键盘 Pro”，售价改为 399 元
历史订单：仍应展示“机械键盘，299 元”
```

订单快照的主要目的：

- 保证历史订单的商品信息和金额不被后续商品修改影响。
- 保证退款、对账、售后等业务能还原当时的成交事实。
- 减少订单展示时对当前商品表的依赖，但这不是保存快照的核心原因。

## 4. 可售库存与锁定库存

| 字段 | 含义 |
| --- | --- |
| `available_stock` | 当前能继续卖给新用户的数量 |
| `locked_stock` | 被待支付订单占用、暂时不能继续出售的数量 |

业务状态流转示例，总库存为 10：

```text
初始：可售 10，锁定 0

创建待支付订单，购买 2 件：可售 8，锁定 2

支付成功：可售 8，锁定 0，2 件商品正式售出

超时取消：可售 10，锁定 0，锁定库存归还
```

注意：`locked_stock` 是业务库存字段，不是数据库行锁。数据库事务提交后，行锁会释放；但订单待支付期间，业务上仍要占用对应库存。

## 5. 创建待支付订单

### 5.1 条件更新锁定库存

用户购买 `quantity` 件商品时，库存更新必须同时校验可售库存是否充足：

```sql
UPDATE product_stock
SET available_stock = available_stock - ?,
    locked_stock = locked_stock + ?
WHERE product_id = ?
  AND available_stock >= ?;
```

参数中的数量均为 `quantity`。

```text
影响行数为 1：锁定库存成功
影响行数为 0：商品不存在或可售库存不足
```

不能只写 `available_stock > 0`：当库存为 1、用户购买 2 件时，条件会错误通过，造成负库存。

### 5.2 本地事务链路

```text
读取商品名称和价格
  ↓
条件更新：可售库存减少、锁定库存增加
  ↓
写入订单：订单号、用户、商品快照、数量、总金额、待支付状态
  ↓
本地事务提交
```

若库存不足，抛出异常，整个本地事务回滚，不应留下新增订单或库存变化。

### 5.3 CloudMall 实现

`OrderService.createPendingOrder()`：

```java
@Transactional
public void createPendingOrder(String orderNo, long userId, String productId, int quantity) {
    ProductSnapshot snapshot = jdbcTemplate.queryForObject(
            "SELECT product_name, price FROM products WHERE product_code = ?",
            productSnapshotRowMapper,
            productId
    );

    int affectedRows = jdbcTemplate.update(
            """
            UPDATE product_stock
            SET available_stock = available_stock - ?,
                locked_stock = locked_stock + ?
            WHERE product_id = ?
              AND available_stock >= ?
            """,
            quantity, quantity, productId, quantity
    );

    if (affectedRows != 1) {
        throw new BusinessException(40902, HttpStatus.CONFLICT, "库存不足");
    }

    // 使用 snapshot 中的名称、成交价、数量和总金额写入 orders。
}
```

## 6. 用户订单列表索引

用户订单列表常见查询：

```sql
SELECT order_no, status, total_amount, created_at
FROM orders
WHERE user_id = ?
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

对应联合索引：

```sql
CREATE INDEX idx_orders_user_created_id
ON orders(user_id, created_at, id);
```

字段顺序原因：

```text
user_id：先过滤当前用户
created_at：满足主排序字段
id：创建时间相同时保证稳定排序，并作为游标的一部分
```

InnoDB 二级索引记录会包含主键值；在索引设计中明确写出 `id`，可以清楚表达稳定排序和游标分页的意图。

## 7. 深分页与游标分页

### 7.1 Offset 分页的边界

```sql
SELECT ...
FROM orders
WHERE user_id = ?
ORDER BY created_at DESC, id DESC
LIMIT 100000, 20;
```

深分页时，数据库通常需要定位并跳过前 100000 条记录，再返回 20 条。偏移量越大，扫描和丢弃的数据越多；若需要回表，成本会进一步增加。

### 7.2 游标分页

若上一页最后一条记录为：

```text
created_at = 2026-08-16 10:00:00
id = 9001
```

下一页查询：

```sql
SELECT order_no, status, total_amount, created_at
FROM orders
WHERE user_id = ?
  AND (
      created_at < ?
      OR (created_at = ? AND id < ?)
  )
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

游标分页从上一页最后一条记录继续向后查询，不需要跳过大量数据。

不能只使用 `created_at` 作为游标：多笔订单可能有相同创建时间。

```text
使用 <=：可能重复
使用 <：可能遗漏同一创建时间内尚未返回的订单
```

因此使用 `created_at + id` 形成稳定、唯一的排序和游标。

### 8.3 库存不足

尝试购买 100 件 `P001`，实际输出：

```text
库存不足创建订单失败：库存不足
库存不足后的订单数量：1
```

说明：失败请求没有创建第二笔订单，也没有改变已成功订单对应的库存状态。

- 当前使用 H2 内存数据库，已验证本地事务、条件更新和订单快照。
- H2 不能替代 MySQL InnoDB 的间隙锁、临键锁、真实死锁日志和生产执行计划。
- 当前 Demo 只覆盖创建待支付订单；支付成功扣减锁定库存、超时取消归还库存将在后续订单链路中继续完善。

## 9. 面试表达

### 为什么库存表要从商品表拆出？

商品基础信息主要用于展示和维护，而库存是高并发写数据，扣减库存时会涉及条件更新、事务和锁冲突。拆分后可以让库存表围绕商品 ID 精确更新，减少商品详情字段被高频写入影响，也更便于后续扩展锁定库存等业务状态。

### 为什么订单需要保存商品快照？

订单需要保存下单时的商品名称和成交单价，保证商品后续改名、改价不会影响历史订单。快照能够支持订单展示、退款、售后和对账，还原用户下单时的实际成交事实。

### 深分页为什么慢，如何优化？

传统 `LIMIT offset, size` 在偏移量很大时，数据库需要扫描并跳过大量前置记录。对于用户订单列表，我会按 `user_id, created_at, id` 建索引，并用 `created_at + id` 作为游标，从上一页末尾继续查询，减少深分页扫描，也保证同一创建时间的数据不重复、不遗漏。

### 创建待支付订单时如何避免超卖？

我会使用 `UPDATE ... SET available_stock = available_stock - ?, locked_stock = locked_stock + ? WHERE product_id = ? AND available_stock >= ?`，并检查受影响行数。库存充足时才写入待支付订单，两个操作放在同一个本地事务内；库存不足则回滚，不会创建订单。后续支付成功需要释放锁定库存，超时取消需要把锁定库存归还到可售库存。
