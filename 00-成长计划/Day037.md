## 2. 索引是什么

索引是数据库为某些列建立的、用于快速定位数据的数据结构。

```sql
SELECT *
FROM products
WHERE product_code = 'P002';
```

没有索引时，数据库可能需要逐行比较；有索引时，可以先定位索引中的目标值，再找到对应数据行。

InnoDB 的索引通常基于 B+ 树。可以理解为：

> B+ 树能逐层缩小查找范围，叶子节点有序，因此适合等值查询、范围查询和排序。

---

## 3. 索引的收益与成本

### 收益

- 减少扫描行数。
- 提升高频查询、排序、关联效率。
- 唯一索引和主键还能保证数据不重复。

### 成本

```text
INSERT：写入数据，同时维护索引
UPDATE：可能维护索引
DELETE：删除数据，同时维护索引
```

索引占用存储空间，也会增加写入成本，因此不能为每个字段都建立索引。

---

## 4. 常见索引类型

| 类型 | 特点 | CloudMall 场景 |
| --- | --- | ---|
| 主键索引 | 唯一、非空，一张表一个 | `products.product_code` |
| 唯一索引 | 值不能重复 | 用户手机号、订单号 |
| 普通索引 | 加速常用查询 | `orders.user_id` |
| 联合索引 | 多列按固定顺序组成一个索引 | `(user_id, status, created_at)` |

商品表中：

```sql
product_code VARCHAR(20) PRIMARY KEY
```

主键同时具备两个价值：

1. 快速按商品编码查询。
2. 作为最终约束，防止重复商品编码。

## 5. 联合索引与最左前缀

```sql
CREATE INDEX idx_orders_user_status_created
ON user_orders(user_id, status, created_at);
```

字段顺序：

```text
user_id → status → created_at
```

最左前缀原则：查询应从索引的最左列开始连续使用。

| 查询条件 | 索引利用情况 |
| --- | --- |
| `WHERE user_id = ?` | 可以使用 |
| `WHERE user_id = ? AND status = ?` | 可以使用 |
| `WHERE user_id = ? AND status = ? AND created_at = ?` | 可以使用 |
| `WHERE status = ?` | 通常无法有效使用 |
| `WHERE created_at = ?` | 通常无法有效使用 |
| `WHERE user_id = ? AND created_at = ?` | 可利用 `user_id`，通常无法充分利用 `created_at` |

SQL 条件书写顺序通常不影响优化器判断；真正影响索引使用的是**建索引时的字段顺序**。

---

## 6. 范围查询的边界

索引：

```text
(user_id, created_at, amount)
```

SQL：

```sql
WHERE user_id = ?
  AND created_at >= ?
  AND amount = ?
```

通常可以有效利用：

```text
user_id + created_at
```

但范围条件 `created_at >= ?` 之后的 `amount`，通常无法再像等值条件一样继续缩小索引扫描范围。

索引设计时，一般将常用等值过滤条件放前面，范围条件放后面。

---

## 7. 常见索引失效或无法充分利用场景

| 场景 | 示例 | 说明 |
| --- | --- | --- |
| 未遵守最左前缀 | `(user_id, status)`，只按 `status` 查询 | 缺少最左字段 |
| 索引列使用函数 | `DATE(created_at) = ?` | 改为时间范围查询 |
| 隐式类型转换 | `VARCHAR` 字段传数字参数 | 参数类型应与字段一致 |
| 前置模糊查询 | `LIKE '%Java'` | 无法从索引起始位置定位 |
| 中间跳列 | `(user_id, status, created_at)`，查询 `user_id + created_at` | 后续列通常无法充分利用 |
| 低选择性条件 | 大部分数据都是同一状态 | 优化器可能选择全表扫描 |
| `OR` 一侧无索引 | `user_id = ? OR product_name = ?` | 可能放弃索引或成本很高 |
| 负向条件 | `!=`、`NOT IN`、`NOT LIKE` | 结果范围可能过大，优化器可能不走索引 |

最终是否使用索引，需要通过 `EXPLAIN` 验证，不能只凭经验判断。

## 8. EXPLAIN 执行计划

```sql
EXPLAIN
SELECT order_no, status, created_at
FROM user_orders
WHERE user_id = 1001
  AND status = 'PAID'
ORDER BY created_at DESC;
```

常见重点字段：

| 字段 | 重点 |
| --- | --- |
| `type` | 访问方式；通常 `const`、`eq_ref`、`ref`、`range` 较好，`ALL` 需要关注 |
| `possible_keys` | 理论可能使用的索引 |
| `key` | 实际使用的索引；`NULL` 表示未使用 |
| `key_len` | 实际使用索引的长度，可辅助判断联合索引利用程度 |
| `rows` | 预计扫描行数，通常越少越好 |
| `Extra` | 额外操作，例如排序、临时表、覆盖索引 |

`Extra` 常见值：

| 值 | 含义 |
| --- | --- |
| `Using index` | 覆盖索引，通常是好现象 |
| `Using where` | 仍需进行条件过滤，很常见 |
| `Using filesort` | 需要额外排序，大数据量时应关注 |
| `Using temporary` | 使用临时表，复杂分组排序时重点排查 |

H2 的 `EXPLAIN` 输出格式与 MySQL 不同，学习时主要观察是否出现索引名称；未来在 MySQL 中重点看 `key`、`rows`、`Extra`。

## 9. CloudMall 订单索引 Demo

### 9.1 建表与索引

```sql
CREATE TABLE user_orders (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    order_no VARCHAR(32) NOT NULL,
    user_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP NOT NULL,
    amount DECIMAL(10, 2) NOT NULL
);

CREATE UNIQUE INDEX uk_user_orders_order_no
ON user_orders(order_no);

CREATE INDEX idx_orders_user_status_created
ON user_orders(user_id, status, created_at);
```

### 9.2 命中联合索引的查询

```sql
EXPLAIN
SELECT order_no, status, created_at
FROM user_orders
WHERE user_id = 1001
  AND status = 'PAID'
ORDER BY created_at DESC;
```

该查询从 `user_id` 开始连续使用联合索引字段。

### 9.3 未遵守最左前缀的查询

```sql
EXPLAIN
SELECT order_no, status, created_at
FROM user_orders
WHERE status = 'PAID'
ORDER BY created_at DESC;
```

缺少最左列 `user_id`，通常不能有效使用 `(user_id, status, created_at)` 联合索引。

### 9.4 真实查询验证

```sql
SELECT order_no, status, created_at
FROM user_orders
WHERE user_id = 1001
  AND status = 'PAID'
ORDER BY created_at DESC;
```

预期：查询到 `O002`、`O001`，且按创建时间倒序排列。

注意：当前 H2 测试数据很少，优化器可能仍选择扫描；Demo 重点是理解索引设计、`EXPLAIN` 与最左前缀，生产效果必须在接近真实的数据量下验证。

## 10. 慢 SQL 排查流程

```text
慢 SQL 日志、APM、监控
  ↓
确定具体 SQL、频率、耗时与参数
  ↓
EXPLAIN 查看执行计划
  ↓
重点检查 key、rows、type、Extra
  ↓
分析索引缺失、联合索引顺序、索引失效写法
  ↓
优化 SQL 或调整索引
  ↓
在接近真实的数据量下验证
  ↓
灰度发布并持续观察接口耗时和数据库负载
```

不要看到慢 SQL 就直接加索引，还要考虑查询频率、选择性、已有索引和写入成本。

## 11. 面试表达

### 索引为什么能加快查询，为什么不能乱建？

索引通常基于 B+ 树，能帮助数据库快速定位数据，减少扫描行数，并提升查询、排序和关联性能。但索引会占用空间，写入、更新和删除时也需要维护，因此应结合高频查询条件、数据量和写入成本设计，不能为每个字段都建立索引。

### 为什么联合索引要遵守最左前缀？

联合索引按字段顺序组织，例如 `(user_id, status, created_at)` 先按用户分组，再按状态和时间排列。查询从 `user_id` 开始连续匹配时，数据库才能快速定位；跳过最左列时，后续字段通常无法形成连续索引范围。

### 线上慢 SQL 怎么排查？

我会先通过慢日志或监控定位具体 SQL、频率和参数，再用 `EXPLAIN` 查看实际使用索引、扫描行数、访问类型和额外排序或临时表。然后结合查询模式优化 SQL 或索引，并在接近真实数据量下验证，最后灰度观察效果。
