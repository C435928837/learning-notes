## 2. 先判断消息积压在哪一段

```text
Producer
  -> Queue
  -> Consumer
  -> ack
```

| 指标 | 含义 | 优先排查方向 |
| --- | --- | --- |
| `Ready` | 消息还在 Queue，尚未投递给消费者 | 消费者是否在线、消费者数量、生产速率与消费速率 |
| `Unacked` | 消息已投递给消费者，但尚未收到 `ack` | 消费代码、线程池、数据库、下游服务、Prefetch |

### 2.1 `Ready` 持续上涨

```text
order.points.queue

Ready：100000
Unacked：20
```

含义：大量积分消息仍在队列中等待，没有被足够快地交给消费者处理。

排查顺序：

```text
1. 消费者是否在线，是否因为异常退出。
2. 消费者实例数是否不足。
3. 消费速率是否长期小于生产速率。
4. 扩容前确认下游数据库和积分服务是否还能承受更多并发。
```

### 2.2 `Unacked` 持续上涨

```text
order.points.queue

Ready：50
Unacked：5000
```

含义：消息已经交给消费者，但消费者迟迟没有完成业务并确认。

优先排查：

```text
消费者异常日志和线程池是否阻塞
数据库连接池是否耗尽
慢 SQL、锁等待、事务是否过长
调用下游服务是否超时
Prefetch 是否过大
```

`Unacked` 高不等于生产者发送有问题，而是消费端“已拿到但没有及时完成确认”的信号。

## 3. Prefetch：限制慢消费者拿走过多消息

### 3.1 是什么

Prefetch 表示一个消费者最多同时持有多少条尚未 `ack` 的消息。

```text
prefetch = 10

RabbitMQ 最多先投递 10 条给该消费者
消费者每成功 ack 一条
RabbitMQ 才继续补一条
```

### 3.2 为什么需要

若某个消费者很慢，却配置了很大的 Prefetch：

```text
prefetch = 10000
-> 慢消费者一次拿到大量消息
-> 消息长期处于 Unacked
-> 其他更快的消费者拿不到这些消息
-> 负载不均衡
```

若这个慢消费者宕机，未确认的消息会被重新投递，可能造成瞬时恢复压力和重复消费。

### 3.3 取舍

| Prefetch 设置 | 优点 | 风险 |
| --- | --- | --- |
| 太小 | 单个消费者持有消息少，故障影响小 | 网络往返更多，吞吐可能偏低 |
| 合理 | 吞吐与消费者保护之间平衡 | 需要根据业务耗时压测调整 |
| 太大 | 减少拉取频率，理论吞吐可能提高 | 慢消费者积压、内存压力、故障重投压力 |

Prefetch 不是越大越好。应结合单条消息大小、平均消费耗时、数据库容量、消费者实例数和压测结果设置。

RabbitMQ 中 Prefetch 用于限制未确认消息数量；`0` 表示不限制，通常需要谨慎使用。[RabbitMQ Consumer Prefetch](https://www.rabbitmq.com/docs/consumer-prefetch)

## 4. 为什么多消费者会影响处理顺序

一个 Queue 只有一个消费者时，消息通常按队列顺序依次交由它处理：

```text
订单 O001：创建 -> 支付 -> 发货
```

多个消费者竞争消费时：

```text
Consumer A 拿到“创建”，但数据库操作很慢
Consumer B 拿到“支付”，且很快处理完成
```

虽然“创建”先投递，“支付”却可能先完成。因此多消费者不能保证全局业务处理完成顺序。

### 4.1 单 Queue、单消费者

```text
优点：逻辑简单，顺序性强。
代价：无法横向扩容；一条慢消息会阻塞所有订单事件。
```

适合并发量低、顺序要求高且业务处理很快的场景，不适合 CloudMall 的高峰订单事件处理。

## 5. 按订单分片，保证局部顺序

CloudMall 不要求所有订单全局有序，只要求同一个订单的状态事件尽量按顺序处理。

```text
orderNo 做稳定哈希
-> 路由到固定的订单分片 Queue
-> 每个分片 Queue 使用一个消费者
```

示例：

```text
O001 -> order.queue.1
O002 -> order.queue.3
O003 -> order.queue.1
```

```text
同一个 orderNo 始终进入同一个 Queue
-> 同一订单事件可按该队列顺序串行处理

不同 orderNo 进入不同 Queue
-> 多个订单可并行处理
```

这里的关键不是“一个订单一个 Queue”，而是使用固定数量的分片 Queue。例如通过 `hash(orderNo) % N` 得到分片编号，并使用该编号作为 Routing Key 的一部分。

```text
Routing Key：order.shard.1
Queue：order.queue.1
```

分片数需要在吞吐与顺序要求之间取舍：分片越多，并行能力越强；分片调整、热点订单和故障恢复的处理也越复杂。

## 6. 顺序路由不是最终正确性保证

即使按 `orderNo` 分片，也可能出现：

```text
先收到“发货”事件
后收到“支付成功”事件
```

原因可能包括生产端事件发布顺序异常、重试、重复投递或历史积压恢复。消费者仍需要校验订单状态机。

```text
收到发货事件
-> 查询订单状态

当前状态为 PAID
-> 允许发货，更新为 SHIPPED

当前状态为 CREATED
-> 不允许发货
-> 延迟重试、暂存等待，或交给补偿任务处理
```

数据库更新使用前置状态条件：

```sql
UPDATE orders
SET status = 'SHIPPED'
WHERE order_no = ?
  AND status = 'PAID';
```

```text
affectedRows = 1
-> 状态转换成功

affectedRows = 0
-> 事件重复、顺序不对或订单状态已发生变化
-> 按业务规则重试、忽略或补偿
```

完整方案：

```text
按 orderNo 分片
+ 每个分片 Queue 单消费者
+ 订单状态机校验
+ 条件更新
+ 幂等与补偿
```

顺序路由降低乱序概率；状态机校验和条件更新才是业务正确性的最终兜底。

## 7. 消息积压如何处理

不能看到 `Ready` 增长就无限扩容消费者：

```text
更多消费者
-> 更多数据库连接和积分更新 SQL
-> 数据库锁竞争、连接池耗尽、慢查询
-> RabbitMQ 积压问题升级为下游数据库故障
```

处理顺序：

```text
1. 判断积压类型：Ready 还是 Unacked。
2. 定位瓶颈：消费者离线、业务代码、数据库、下游服务或生产突增。
3. 确认下游容量后，逐步扩容消费者。
4. 必要时限制生产端，或降级短信、积分等非核心业务。
5. 对超过时效的消息按业务规则补偿、丢弃或转入死信队列。
```

### 7.1 CloudMall 场景

大促后 `order.points.queue` 的 `Ready` 快速增长：

```text
先检查积分消费者是否存活、消费速率是否下降
-> 检查积分数据库连接池和慢 SQL
-> 数据库容量允许时逐步增加积分消费者实例
-> 必要时暂停非核心积分发放或降低积分实时性
-> 订单创建和库存扣减不应被积分积压阻塞
```

## 8. 监控与告警

至少应关注：

| 指标 | 关注原因 |
| --- | --- |
| `messages_ready` | 发现消费者供给不足或消费速率落后 |
| `messages_unacknowledged` | 发现消费者处理慢、下游超时或 Prefetch 过大 |
| `publish rate` | 判断生产压力 |
| `deliver/ack rate` | 判断消费是否跟上生产 |
| `consumer count` | 判断消费者是否掉线或扩容是否生效 |
| Broker 内存、磁盘、CPU | 防止 Broker 因资源耗尽影响消息服务 |
| 死信队列消息数 | 发现永久异常、重试失败或补偿积压 |

开发环境可通过管理后台观察 Queue、Consumer 和消息指标；生产环境通常使用 Prometheus 采集指标、Grafana 展示趋势并配置告警。RabbitMQ 官方推荐 Prometheus 与 Grafana 用于生产监控。[RabbitMQ Monitoring](https://www.rabbitmq.com/docs/monitoring)

## 9. 面试表达

### 9.1 RabbitMQ 消息积压如何排查和处理？

> 我会先区分 Ready 和 Unacked。Ready 持续增长说明消息还在队列中等待，优先检查消费者是否在线、实例数是否不足，以及生产速率是否大于消费速率。Unacked 持续增长说明消息已经投递给消费者但业务没有及时完成，我会重点检查消费者线程池、数据库连接池、慢 SQL、锁等待和下游超时。确认下游容量后再逐步扩容消费者，不能盲目扩容，否则会把 RabbitMQ 的积压压力转移为数据库压力。必要时对短信、积分等非核心业务限流或降级，订单和库存等核心链路保持同步正确性。

### 9.2 Prefetch 为什么能保护消费者？

> Prefetch 限制单个消费者未 ack 消息的最大数量。消费者处理较慢时，它可以避免一个实例提前拿走大量消息，造成 Unacked 积压和负载不均衡；消费者宕机时也能减少需要重新投递的消息量。Prefetch 太小会影响吞吐，太大又会让慢消费者占用过多消息，需要结合消费耗时、消息大小、下游容量和压测结果设置。

### 9.3 如何保证同一订单事件的处理顺序？

> 全局顺序会限制并发，我通常只保证同一订单的局部顺序。将 orderNo 做稳定哈希，路由到固定分片 Queue，每个分片由单消费者串行处理。不同订单可以落到不同分片并行消费。同时不能只依赖消息顺序，消费者还要校验订单状态机，例如发货只能从 PAID 更新到 SHIPPED，并通过带前置状态的条件更新、幂等和补偿作为最终兜底。
