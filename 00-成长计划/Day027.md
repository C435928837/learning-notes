## 三、分代收集思想

### 1. 是什么

分代收集是 JVM 按对象存活时间，对堆中对象进行逻辑分组并采用不同回收频率的思想。

```text
新生代：大多数刚创建、生命周期短的对象
老年代：经历多次 GC 后仍长期存活的对象
```

### 2. 为什么

依据是大多数对象“朝生夕死”：

```text
大量短生命周期对象
-> 主要集中在新生代
-> 高频、小范围回收
-> 不必每次扫描整个堆
```

好处：

- 减少每次 GC 的扫描范围。
- 更高效地回收请求 DTO、临时集合、序列化中间对象等。
- 长期存活对象不需要参与每一次 Young GC。

### 3. 怎么做

```text
新对象
-> Eden
-> Young GC 后存活对象进入 Survivor
-> 经历多次 Young GC，年龄增长
-> 达到条件或 Survivor 放不下时，晋升老年代
```

新生代的逻辑结构：

```text
Eden + Survivor 0 + Survivor 1
```

对象通常在两块 Survivor 区之间复制。Survivor 区不单独 GC，而是随 Young GC 一起处理。

## 四、GC 类型

| 类型 | 回收范围 | 触发情况 |
|---|---|---|
| Young GC / Minor GC | 新生代 Region | Eden 无法继续分配对象 |
| Old GC / Major GC | 老年代相关区域 | 老年代空间压力增大，具体实现因收集器而异 |
| Mixed GC | 新生代 + 部分老年代 Region | G1 并发标记结束后 |
| Full GC | 通常涉及整个堆或更大范围 | 内存严重紧张、普通回收无法满足分配需求等 |

注意：

```text
Major GC 的具体含义会随 JVM 和收集器实现变化。
不要机械地理解为“Major GC 一定只回收老年代”。
```

## 五、常见垃圾收集器

| 收集器 | 核心取向 | 适用场景 | 主要特点 |
|---|---|---|---|
| Serial GC | 简单、资源少 | 小内存、小型程序 | 单线程 Stop-The-World |
| Parallel GC | 吞吐量优先 | 批处理、离线计算 | 多线程并行回收，允许更长停顿 |
| CMS | 历史低停顿方案 | 旧系统知识点 | 存在内存碎片问题，新项目不选 |
| G1 | 停顿可预测 | 常规服务端、大堆应用 | Region、并发标记、Mixed GC |
| ZGC | 极低停顿 | 强低延迟、大堆服务 | 并发回收，资源开销更高 |
| Shenandoah | 极低停顿 | 强低延迟服务 | 并发整理，需结合运行环境评估 |

## 六、G1 收集器

### 1. 是什么

G1 将整个堆划分为多个大小相等的 Region：

```text
Region 1：Eden
Region 2：Eden
Region 3：Survivor
Region 4：Old
Region 5：Old
```

Region 的角色可以动态变化，不再是物理连续的新生代和老年代。

### 2. 为什么

G1 会优先回收垃圾比例高、存活对象少的 Region：

```text
Garbage First
-> 优先处理回收收益高的 Region
-> 尽量控制停顿时间
```

### 3. 怎么做

```text
Young GC
-> 回收新生代 Region

并发标记
-> 识别老年代等区域中的存活对象

Mixed GC
-> 回收新生代 Region + 部分回收收益高的老年代 Region
```

若内存极度紧张、并发回收无法及时释放空间，G1 仍可能发生 Full GC。

### 4. 常见参数

```text
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-Xlog:gc*
```

`MaxGCPauseMillis` 是停顿时间目标，不是严格保证。

## 七、GC 日志回看

我的 GC 日志：

```text
[2.291s][info][gc,heap     ] GC(34) Eden regions: 0->0(17)
[2.291s][info][gc,heap     ] GC(34) Survivor regions: 2->2(3)
[2.291s][info][gc,heap     ] GC(34) Old regions: 5->5
[2.291s][info][gc,heap     ] GC(34) Humongous regions: 10->0
[2.291s][info][gc,metaspace] GC(34) Metaspace: 6743K(7040K)->6743K(7040K) NonClass: 6008K(6144K)->6008K(6144K) Class: 734K(896K)->734K(896K)
[2.291s][info][gc          ] GC(34) Pause Young (Concurrent Start) (G1 Humongous Allocation) 14M->4M(32M) 1.062ms

```

我观察到的 GC 类型：

```text
收集器：G1
GC 类型：Young GC
触发原因：G1 Humongous Allocation
停顿时间：1.062ms
堆变化：14M->4M(32M)
```

我的理解：

```text
Eden 0->0(17)：GC 后 Eden 没有存活对象，目标容量为 17 个 Region
Survivor 2->2(3)：有 2 个 Survivor Region 仍存活
Old 5->5：本次没有老年代 Region 变化
Humongous 10->0：10 个大对象 Region 被回收
14M->4M(32M)：本次回收了约 10MB，剩余存活对象约 4MB
```

## 八、算法题：有效的括号

题目要求：

```text
给定只包含 ()、[]、{} 的字符串，判断括号是否有效匹配。
```

### 解题思路

```text
遍历字符串；遇到左括号入栈，遇到右括号时弹出栈顶元素，判断两者是否匹配；最后栈为空则有效。
```

### Java 代码

```java
public boolean isValid(String s) {
        boolean result = false;
        char[] chars = s.toCharArray();
        Deque<Character> deque = new ArrayDeque<>();
        for(char c : chars){
            if(c == '(' || c == '[' || c == '{'){
                deque.push(c);
            } else {
                if (deque.isEmpty()) return false;

                char top = deque.pop();
                if (c == ')' && top != '(') return false;
                if (c == '}' && top != '{') return false;
                if (c == ']' && top != '[') return false;
            } 
        }
        return deque.isEmpty();
    }

```

### 复杂度

```text
时间复杂度：O(n)
空间复杂度：O(n)
```

## 九、面试口述

### 题目 1：为什么 JVM 要采用分代收集？对象通常如何在新生代和老年代之间流转？

我的回答：

```text
分代收集是 JVM 根据对象存活周期管理堆内存的思想。因为大多数对象朝生夕死，所以对象通常先分配在新生代；新生代满时触发 Young GC，死亡对象直接回收，存活对象经过多次回收后会晋升到老年代。这样 JVM 可以高频、低成本地回收短生命周期对象，而不必每次扫描整个堆。老年代对象存活时间更长，回收频率更低，但一旦发生老年代压力或 Full GC，停顿风险通常更值得关注。

```

### 题目 2：Young GC、Mixed GC、Full GC 有什么区别？为什么线上需要关注 Full GC？

我的回答：

```text
Young GC：回收eden区和surivor区的对象
Mixed GC：Young GC和回收部分老年代对象
Full GC：整个堆回收
线上最需要关注的是 Full GC 的频率和停顿时间，因为它通常说明老年代压力、对象晋升过快、内存参数不合理，或者存在内存泄漏等问题。
```

### 题目 3：G1 的核心特点是什么？适合什么场景？

我的回答：

```text
特点是把堆划分成一个个大小相等的region，回收逻辑依旧保持eden、surivor、和老年代，只是不再物理划分这些区，按垃圾回收收益选择 Region、并发标记、Mixed GC、尽量控制停顿目标；
适合大堆内存的服务端应用的低停顿回收
```
