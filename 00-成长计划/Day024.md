## 3. 类加载器基础

| 类加载器 | 主要加载内容      | 我的理解                                                                                    |
| --- |-------------|-----------------------------------------------------------------------------------------|
| Bootstrap ClassLoader | 加载java的核心类  | JVM 最底层的类加载器，负责加载 java.lang.String、java.util.ArrayList 等核心类库；它由本地代码实现，所以获取到的加载器通常是 null |
| Platform ClassLoader | 加载jdk相关的模块类 |  位于 Bootstrap 和 Application 之间，负责加载 JDK 平台模块相关类；JDK 8 中类似角色叫 Extension ClassLoader                                                                                       |
| Application ClassLoader | 加载业务类       | 默认加载应用 Classpath 中的业务代码和第三方依赖，例如 CloudMall 的业务类、Spring 和 MyBatis 等依赖                                                                                        |

为什么 `String.class.getClassLoader()` 返回 `null`：

>Bootstrap ClassLoader由本地方法实现，不是普通java的classloader对象

需要注意的边界：

- [ ] Bootstrap ClassLoader 由 JVM 本地代码实现，不是普通 Java `ClassLoader` 对象。
- [ ] JDK 8 中类似 Platform ClassLoader 的角色通常称为 Extension ClassLoader。
- [ ] JVM 不只有三个类加载器，还可以自定义类加载器。

## 4. 双亲委派模型

加载流程：

```text
检查当前加载器是否已加载
  ↓
委托父加载器加载
  ↓
父加载器无法加载
  ↓
当前加载器调用 findClass() 尝试加载
```

`loadClass()`、`findLoadedClass()`、`findClass()` 的职责：

| 方法 | 职责       |
| --- |----------|
| `loadClass()` | 负责双亲委派流程 |
| `findLoadedClass()` | 判断是否已加载  |
| `findClass()` | 加载类      |

为什么需要双亲委派：

- [ ] 保护 JDK 核心类。
- [ ] 避免重复加载同一个类。
- [ ] 减少类型冲突。
- [ ] 

我的总结：

>双亲委派机制首先在当前类加载器判断是否已加载，已加载直接返回，未加载则委派父加载类判断，如果父加载类找不到则由当前类加载器尝试加载

## 5. 类身份与例外场景

类的唯一身份：

```text
全限定类名 + 类加载器
```

为什么不同类加载器加载同名类后不能直接强制转换：

>保护java的核心类，以父加载类优先加载

哪些场景可能不完全遵循双亲委派：

- [ ] Tomcat
- [ ] OSGi
- [ ] 插件化框架
- [ ] 

原因：

>omcat、OSGi、插件化框架需要隔离不同应用或插件的依赖，并支持不同版本类库共存，因此可能采用子优先或其他自定义加载策略；但通常仍会优先保护 JDK 核心类

## 6. 线程上下文类加载器

获取当前线程上下文类加载器：

```java
Thread.currentThread().getContextClassLoader();
```

它解决的问题：

>TCCL 解决父加载器加载的 JDK 或框架代码无法直接看到子加载器业务实现的问题。例如 ServiceLoader、JDBC 等可以通过当前线程 TCCL 查找应用或插件提供的实现类。在线程池中必须恢复原 TCCL，避免复用线程长期持有旧插件 ClassLoader，导致类无法卸载和元空间泄漏

典型使用场景：

>TCCL 最经典的用途是 SPI。它让父加载器加载的框架或 JDK 代码，能够通过当前线程找到子加载器中的业务实现类

为什么在线程池或插件场景中要恢复原 TCCL：

>防止下个线程也加载旧加载类，及时释放加载类，避免元空间内存泄漏

## 8. 90 秒口述题

### 8.1 什么是双亲委派模型？它解决什么问题？

我的回答：

>双亲委派是类加载器默认采用的父优先加载模型。当前加载器先检查类是否已加载，未加载则委托父加载器；父加载器无法加载时，当前加载器才调用 findClass() 尝试加载。它用于保护 JDK 核心类、避免重复加载和减少类型冲突

### 8.2 为什么两个不同类加载器加载同名类，不能直接互相强制转换？

我的回答：

>类的唯一身份由全限定类名和类加载器共同决定。两个不同类加载器加载同名类，会得到两个不同的 Class 对象，因此即使名称完全相同，也不能直接强制转换，否则可能抛出 ClassCastException
