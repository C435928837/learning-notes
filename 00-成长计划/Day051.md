## 2. OpenFeign 是什么

OpenFeign 是 Spring Cloud 中的声明式 HTTP 客户端。开发者通过 Java 接口描述远程服务 API，Spring 在启动时为接口创建代理对象；调用接口方法时，代理会构造并发送 HTTP 请求。

没有 Feign 时，调用方通常要手写 URL、HTTP 请求、序列化、反序列化和异常处理：

```java
String url = "http://10.0.0.1:8081/api/stocks/deduct";
// 手动构造请求、发送 HTTP、处理响应和异常
```

使用 Feign 后，以接口表达远程调用：

```java
@FeignClient(name = "stock-service")
public interface StockClient {

    @PostMapping("/api/stocks/deduct")
    StockDeductResponse deduct(@RequestBody StockDeductRequest request);
}
```

订单服务像注入普通 Bean 一样注入并调用：

```java
@Service
public class OrderService {

    private final StockClient stockClient;

    public OrderService(StockClient stockClient) {
        this.stockClient = stockClient;
    }

    public void createOrder() {
        StockDeductResponse result = stockClient.deduct(
                new StockDeductRequest("O001", "P001", 2)
        );
    }
}
```

OpenFeign 是“声明式调用方式”，不是库存一致性方案。它让 HTTP 调用代码更清晰，但无法自动解决超卖、幂等、超时结果不确定或跨服务事务问题。

## 3. OpenFeign 调用链

```text
OrderService
-> StockClient 接口代理
-> stock-service 服务名
-> 服务发现获取健康实例
-> LoadBalancer 选择一个实例
-> HTTP 调用库存服务
-> 反序列化响应为 StockDeductResponse
```

启动类需要开启 Feign Client 扫描：

```java
@SpringBootApplication
@EnableFeignClients
public class OrderApplication {
}
```

`@FeignClient(name = "stock-service")` 中的 `name` 是客户端名称。在注册中心环境中，调用方通过该服务名获得实际实例地址，再由客户端负载均衡选择一个健康实例。

```text
stock-service
  ├─ 10.0.0.1:8081  UP
  └─ 10.0.0.2:8081  UP
```

订单服务不应写死某个实例 IP。库存服务扩容、下线、发布或容器重建后，注册中心和负载均衡可以动态选择健康实例。

Spring Cloud OpenFeign 支持 Spring MVC 注解和 Spring Cloud LoadBalancer；`@FeignClient` 的服务名可用于发现实际服务地址。[Spring Cloud OpenFeign Features](https://docs.spring.io/spring-cloud-openfeign/reference/spring-cloud-openfeign.html)

## 4. 跨服务接口使用 DTO

### 4.1 请求和响应 DTO

订单服务调用库存服务时，应使用面向远程接口的 DTO：

```java
public record StockDeductRequest(
        String orderNo,
        String productCode,
        int quantity
) {
}

public record StockDeductResponse(
        boolean success,
        String message
) {
}
```

字段含义：

| 字段 | 作用 |
| --- | --- |
| `orderNo` | 扣减请求的业务唯一标识，可用于幂等判断 |
| `productCode` | 被扣减库存的商品标识 |
| `quantity` | 扣减数量，库存服务必须校验大于 0 |
| `success` / `message` | 向调用方表达业务结果 |

### 4.2 为什么不能复用 `StockEntity`

`StockEntity` 是库存服务内部的数据库实体，可能包含 ORM 映射、表字段、库存计算细节和内部状态。订单服务直接依赖它会导致：

```text
库存服务修改表字段或内部实体
-> 订单服务也可能被迫修改、重新编译和发布

库存服务内部实现细节泄漏
-> 服务边界被破坏
```

DTO 是稳定的远程接口契约。库存服务可以调整表结构、索引和内部实现，只要 DTO 契约保持兼容，订单服务就不需要同步修改。

### 4.3 为什么不能直接操作库存服务数据库

```text
订单服务直接 UPDATE 库存表
-> 绕过库存服务的库存校验、条件更新和幂等逻辑
-> 破坏库存服务的数据所有权
-> 数据库结构变成跨服务耦合点
```

库存服务应独立负责库存扣减、库存不足判断、扣减幂等和库存状态维护；订单服务通过公开 API 请求结果。

## 5. 超时不等于库存扣减失败

### 5.1 超时的三种可能

订单服务调用库存扣减发生读取超时时，不能直接断言库存未扣：

```text
1. 请求根本没有到达库存服务。
2. 库存服务正在处理，尚未完成。
3. 库存服务已扣减成功，但响应在网络中丢失或返回过慢。
```

因此：

```text
Feign 超时
不等于
库存扣减失败
```

### 5.2 连接超时与读取超时

| 类型 | 含义 | 常见原因 |
| --- | --- | --- |
| 连接超时 | 在指定时间内无法建立连接 | 实例不可达、网络异常、端口未监听 |
| 读取超时 | 已建立连接，但在指定时间内未收到完整响应 | 下游处理慢、数据库慢、接口阻塞 |

超时需要合理配置，避免订单服务线程无限等待下游服务。但超时时间不能随意设置得极短，否则正常的慢请求也会被误判失败。

## 6. 查询和库存扣减的重试边界

### 6.1 商品详情查询

商品详情查询是只读操作：

```text
查询超时
-> 有限次重试通常不会修改业务数据
-> 失败后可读取缓存或提示“信息暂不可用”
```

### 6.2 库存扣减

库存扣减是写操作：

```text
库存扣减超时
-> 可能已经执行成功
-> 无保护地重复请求
-> 同一订单可能重复扣减库存
```

库存扣减在重试前，至少需要两个不同层次的保护：

| 目标 | 典型方案 |
| --- | --- |
| 防超卖 | `stock >= quantity` 的条件更新、Redis Lua 原子判断和扣减等 |
| 防同一订单重复扣减 | `orderNo` 幂等记录、唯一约束、已处理结果复用 |

```text
条件更新防止库存被扣成负数
不等于
orderNo 幂等防止同一订单扣减两次
```

库存服务收到同一个 `orderNo` 的重复请求时，应直接返回第一次处理结果，而不是再次扣减。满足这个前提后，订单服务才可以设计有限重试或查询扣减结果。

## 7. 业务异常与系统异常

库存服务调用结果不能全部按“异常重试”处理：

| 结果 | 语义 | 订单服务处理 |
| --- | --- | --- |
| `404` 商品不存在 | 明确业务结果 | 不重试，返回商品不存在 |
| `409` 库存不足 | 明确业务结果 | 不重试，返回库存不足 |
| 连接超时 / 读取超时 | 结果不确定 | 依赖幂等后有限重试或查询结果 |
| `500` | 库存服务内部异常 | 结合幂等、异常类型和系统负载谨慎处理 |

`409 Conflict` 在 HTTP 层通常会使 Feign 进入错误处理流程，但业务语义上它是“库存不足”的确定结果，而不是网络抖动。订单服务应将其转换为可识别的业务异常，例如 `StockInsufficientException`，而不是自动重试。

OpenFeign 可通过 `ErrorDecoder` 等机制将远程错误响应转换为调用方可处理的异常；当前默认重试器为 `Retryer.NEVER_RETRY`，避免在未知幂等边界下自动放大写操作风险。[Spring Cloud OpenFeign Features](https://docs.spring.io/spring-cloud-openfeign/reference/spring-cloud-openfeign.html)

## 8. 超时、熔断与降级边界

```text
超时：限制一次调用最多等待多久
重试：对可恢复且幂等的请求有限再次尝试
熔断：持续失败时暂时快速失败，防止故障扩散
降级：下游不可用时提供受控的有限能力或结果
```

CloudMall 场景：

| 场景 | 可选处理 | 不应做的事 |
| --- | --- | --- |
| 商品详情查询失败 | 缓存、默认展示、提示稍后重试 | 无限重试导致级联压力 |
| 积分查询失败 | 返回“积分信息暂不可用” | 阻塞订单主流程 |
| 库存扣减超时 | 幂等后有限重试、查询处理结果、补偿或对账 | 直接重试、直接返回下单成功 |
| 库存不足 | 返回业务失败 | 当作网络异常重试 |

降级不是伪造成功。库存扣减、支付、订单创建等核心写操作发生故障时，必须保持业务状态可追踪，并通过幂等、补偿和对账保证最终正确性。

## 9. CloudMall 调用设计

```text
订单服务创建订单
-> 调用 StockClient.deduct(orderNo, productCode, quantity)
-> Nacos 根据 stock-service 返回健康实例
-> LoadBalancer 选择实例
-> Feign 发起 HTTP 请求

库存服务处理
-> 通过 orderNo 判断是否已经扣减
-> 未处理：校验 stock >= quantity，执行条件更新并记录处理结果
-> 已处理：返回第一次扣减结果

订单服务处理响应
-> 扣减成功：继续创建或确认订单
-> 库存不足：返回业务失败，不重试
-> 超时：按 orderNo 查询结果或在幂等前提下有限重试
```

## 10. 面试表达

### 10.1 OpenFeign 如何完成一次服务调用？

> OpenFeign 是声明式 HTTP 客户端。我通过 `@FeignClient` 定义远程服务接口，通过 Spring MVC 注解声明请求路径、方法和参数。调用接口方法时，Spring 创建的代理会根据服务名从注册中心获取健康实例，再交给客户端负载均衡选择实际地址并发起 HTTP 请求，最后将响应转换为 DTO。它简化了远程调用代码，但不解决业务幂等和分布式一致性，需要由库存服务的条件更新、orderNo 幂等和补偿机制保证。

### 10.2 库存扣减超时如何处理？

> 超时不代表库存扣减失败，因为请求可能未到达、正在处理，或者已经成功但响应丢失。库存服务需要先以 orderNo 做幂等，并通过 `stock >= quantity` 的条件更新防止超卖。具备这些保护后，订单服务可以有限重试或按 orderNo 查询处理结果；不能在没有幂等保障时盲目重试，也不能直接向用户返回下单成功。

### 10.3 返回库存不足时为什么不重试？

> 库存不足是一个确定的业务结果，不是网络抖动。虽然 HTTP 409 在 Feign 层通常进入错误处理，但订单服务应将其映射为库存不足业务异常并直接返回，不应该自动重试。重试不会创造库存，只会增加服务压力。
