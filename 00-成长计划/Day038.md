## 2. 并发事务会出现什么问题

### 2.1 脏读

事务 B 读到了事务 A 尚未提交的数据；若事务 A 后续回滚，事务 B 读到的数据从最终状态看从未真正生效。

```text
初始库存：1
事务 A：更新库存为 0，但未提交
事务 B：读取库存为 0
事务 A：回滚，库存最终仍为 1
```

风险：事务 B 可能基于一个最终不存在的数据做业务判断，例如错误地拒绝用户下单。

### 2.2 不可重复读

同一事务中，两次读取同一条已存在记录，读到了不同内容。

```text
事务 A：第一次读取商品价格，得到 99
事务 B：将价格更新为 109 并提交
事务 A：第二次读取同一商品，得到 109
```

关注点：**同一行记录的内容发生变化**。

### 2.3 幻读

同一事务使用相同条件查询，两次得到的结果集行数不同。

```text
事务 A：查询用户 1001 的已支付订单，共 2 条
事务 B：新增一条用户 1001 的已支付订单并提交
事务 A：再次按相同条件查询，共 3 条
```

关注点：**符合查询条件的记录凭空多出或少了**。

### 2.4 不可重复读与幻读的区别

```text
不可重复读：同一条已有记录的字段值改变
幻读：符合条件的记录集合改变
```

## 3. 四种事务隔离级别

| 隔离级别 | 中文名 | 脏读 | 不可重复读 | 幻读 | 取舍 |
| --- | --- | --- | --- | --- | --- |
| `READ UNCOMMITTED` | 读未提交 | 可能 | 可能 | 可能 | 一致性弱，业务中很少使用 |
| `READ COMMITTED` | 读已提交 | 不会 | 可能 | 可能 | 每次读取最新已提交数据 |
| `REPEATABLE READ` | 可重复读 | 不会 | 不会 | 需结合具体读类型理解 | MySQL InnoDB 默认 |
| `SERIALIZABLE` | 可串行化 | 不会 | 不会 | 不会 | 一致性最强，并发最低 |

隔离级别越高，数据库需要付出更多协调成本，例如锁等待、冲突处理或版本维护，因此通常并发能力越低。

但 InnoDB 并非完全依赖锁。普通读可借助 MVCC 读取合适的历史版本，从而减少读写互相阻塞。

## 4. MVCC：让读写更好地并发

### 4.1 是什么

MVCC（Multi-Version Concurrency Control，多版本并发控制）为一行数据维护版本信息，使不同事务能够读取自己应该看到的数据版本。

它主要缓解**读写并发冲突**，不是用来解决两个事务同时修改同一行的写写冲突。

### 4.2 为什么需要 MVCC

如果读操作总是等待写操作释放锁，商品详情、订单列表等高频查询会被更新操作阻塞。

MVCC 允许普通查询读取历史可见版本，使读取与更新在很多场景下可以并发执行。

### 4.3 两个关键概念

| 概念 | 作用 |
| --- | --- |
| Undo Log | 保存旧版本信息，用于构造历史数据版本 |
| Read View | 定义当前事务可见的事务范围，决定读取哪个版本 |

示例：

```text
初始价格：99
事务 A 开始并读取价格：99
事务 B 将价格更新为 109 并提交
事务 A 再次普通查询：在可重复读下通常仍读取 99
```

事务 A 不需要一直锁住商品价格行，而是依据 Read View 从版本链中获得自己可见的旧版本。

## 5. 快照读与当前读

### 5.1 快照读

普通 `SELECT` 通常属于快照读：

```sql
SELECT stock
FROM product_stock
WHERE product_id = 'P001';
```

快照读依据事务的可见性规则读取合适的版本。在可重复读隔离级别下，同一事务的多次普通查询通常可获得一致结果。

适合：商品详情、订单列表、报表等读取场景。

### 5.2 当前读

`UPDATE`、`DELETE`、`INSERT` 和 `SELECT ... FOR UPDATE` 等需要基于当前数据完成修改或加锁的操作，属于当前读。

```sql
SELECT stock
FROM product_stock
WHERE product_id = 'P001'
FOR UPDATE;

UPDATE product_stock
SET stock = stock - 1
WHERE product_id = 'P001';
```

当前读读取最新已提交版本，并在需要时通过锁保证修改基于真实的当前数据。

适合：库存扣减、余额修改、支付状态变更等不能依据历史版本决策的场景。

## 6. CloudMall：条件更新扣库存

### 6.1 不安全写法

```java
int stock = jdbcTemplate.queryForObject(
        "SELECT stock FROM product_stock WHERE product_id = ?",
        Integer.class,
        productId
);

if (stock > 0) {
    jdbcTemplate.update(
            "UPDATE product_stock SET stock = stock - 1 WHERE product_id = ?",
            productId
    );
}
```

两个请求可能先后都查询到库存为 `1`，随后分别扣减，导致库存变为负数。

### 6.2 正确写法

```sql
UPDATE product_stock
SET stock = stock - 1
WHERE product_id = ?
  AND stock > 0;
```

```java
@Transactional
public boolean deductStock(String productId) {
    int affectedRows = jdbcTemplate.update(
            "UPDATE product_stock SET stock = stock - 1 WHERE product_id = ? AND stock > 0",
            productId
    );
    return affectedRows == 1;
}
```

受影响行数含义：

```text
1：库存充足，扣减成功
0：库存不足或商品不存在，扣减失败
```

### 6.3 为什么能避免最后一件被重复扣减

假设库存为 `1`：

1. 请求 A 先执行条件更新，将库存从 `1` 更新为 `0`。
2. 请求 B 执行同一条 SQL 时，会等待冲突处理完成。
3. 请求 A 提交后，请求 B 基于最新库存 `0` 判断 `stock > 0`，条件不成立，更新行数为 `0`。

因此，判断和扣减由一条 SQL 原子完成，只有一个请求会成功。

### 6.4 Demo 验证

在 `schema.sql` 中准备：

```sql
INSERT INTO product_stock(product_id, stock) VALUES ('P002', 1);
```

启动时连续扣减两次 `P002`，实际输出：

```text
第一次条件扣库存：true
第二次条件扣库存：false
条件扣减后的 P002 库存：0
```

### 6.5 方案边界

- 条件更新适用于多个应用实例共用同一个数据库的场景，不依赖 JVM 内存。
- `affectedRows = 0` 无法仅凭这一条 SQL 区分“商品不存在”和“库存不足”；若业务需要精确提示，需要额外查询或在业务层定义统一提示。
- 它解决的是数据库库存不被扣成负数，不等于订单创建、支付、消息投递一定成功。
- 高并发秒杀通常还需要 Redis Lua 预扣、订单幂等、消息可靠投递、失败补偿或对账；数据库条件更新可作为最终兜底。

## 7. 面试表达

### 什么是 MVCC？

MVCC 是多版本并发控制。InnoDB 通过 Undo Log 保存历史版本，并通过 Read View 判断当前事务能看到哪些版本。它主要解决读写并发冲突，使普通查询通常不需要等待写操作释放锁；但两个事务同时修改同一行数据的写写冲突仍需依赖锁等机制处理。

### 快照读和当前读有什么区别？

普通 `SELECT` 通常是快照读，读取满足当前事务可见性规则的数据版本，适合商品详情和订单列表等查询。`UPDATE`、`SELECT ... FOR UPDATE` 等属于当前读，需要基于最新已提交数据执行，并在必要时加锁，适合库存和余额等不能读取旧数据后再修改的场景。

### 多实例环境下如何避免库存超卖？

对于共用同一数据库的场景，我会使用 `UPDATE ... SET stock = stock - 1 WHERE product_id = ? AND stock > 0`，并检查受影响行数。判断库存和扣减库存由一条 SQL 原子完成，成功更新一行才允许后续创建订单。高并发秒杀还需结合 Redis Lua、订单幂等、消息可靠性、补偿和对账，数据库条件更新作为最终兜底。
