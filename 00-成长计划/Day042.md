## 2. 三类缓存问题总览

| 问题 | 核心现象 | 数据是否存在 | 影响范围 |
| --- | --- | --- | --- |
| 缓存穿透 | 请求持续查询不存在的数据 | 缓存和数据库都不存在 | 某类非法或不存在请求 |
| 缓存击穿 | 一个热点 Key 过期 | 数据库存在，缓存刚失效 | 单个热点 Key |
| 缓存雪崩 | 大量 Key 同时失效或 Redis 故障 | 数据通常存在 | 大量 Key 或整个缓存服务 |

共同风险：大量请求绕过 Redis，集中访问数据库，造成数据库连接、CPU、慢 SQL 和接口超时压力。

---

## 3. 缓存穿透

### 3.1 是什么

缓存穿透是大量请求查询缓存和数据库中都不存在的数据。

```text
请求商品 P999
  ↓
Redis 未命中
  ↓
数据库未命中
  ↓
Redis 中仍无结果
  ↓
下一次请求继续访问数据库
```

若有人不断请求不存在的商品编码，大量无效请求会持续穿透到数据库。

### 3.2 方案一：缓存空值

数据库未查询到商品时，也缓存一个空标记，并设置较短 TTL：

```text
Key：product:detail:P999
Value：__NULL__
TTL：2 分钟
```

后续请求命中空标记后，直接返回“商品不存在”，不再查询数据库。

空值缓存必须使用短 TTL，避免商品后来创建后长期读取到旧的“不存在”结果。

### 3.3 方案二：布隆过滤器

布隆过滤器可以提前判断一个商品 ID 是否可能存在：

```text
布隆过滤器明确不存在
→ 直接返回，不访问 Redis 和数据库

布隆过滤器可能存在
→ 再查询 Redis 和数据库
```

布隆过滤器的特点：

```text
可能误判存在：实际不存在的数据仍可能继续查询数据库
不会误判不存在：已加入的商品 ID 不会被错误拦截
```

因此它适合作为数据库前的快速过滤层，但不能代替数据库最终校验。

### 3.4 方案三：参数校验

请求商品接口时，先校验商品编码格式、长度和空值等明显非法参数。非法请求应直接拒绝，不进入 Redis 和数据库。

## 4. 缓存击穿

### 4.1 是什么

缓存击穿是一个热点 Key 过期的瞬间，大量并发请求同时发现缓存未命中，全部回源数据库。

```text
热门商品 P001 的缓存过期
  ↓
大量用户同时查询 P001
  ↓
全部 Redis 未命中
  ↓
大量请求同时查询数据库
```

穿透查询的是不存在的数据；击穿查询的是数据库中存在、但缓存刚失效的热点数据。

### 4.2 方案一：互斥锁重建缓存

缓存未命中后，只有一个请求获得重建锁：

```text
请求 A：获得锁 → 查询数据库 → 重建缓存 → 释放锁
请求 B、C：未获得锁 → 短暂等待后重试缓存，或降级返回
```

Redis 分布式锁的基础形式：

```text
SET lock:product:detail:P001 token NX PX 10000
```

| 参数 | 含义 |
| --- | --- |
| `NX` | 锁不存在时才设置成功 |
| `PX 10000` | 锁 10 秒后自动过期，避免异常导致永久占用 |
| `token` | 锁的唯一标识，释放时应校验，避免误删其他请求的锁 |

互斥锁的特点：缓存重建期间，部分请求需要等待；优点是重建完成后通常能读取较新的数据。

### 4.3 方案二：逻辑过期

逻辑过期在缓存 Value 中保存业务过期时间，而不完全依赖 Redis Key 的短物理 TTL：

```json
{
  "data": {
    "productCode": "P001",
    "productName": "机械键盘",
    "price": 299.00
  },
  "logicalExpireAt": "2026-08-24T20:30:00"
}
```

读取逻辑：

```text
当前时间小于 logicalExpireAt
→ 直接返回缓存数据

当前时间大于等于 logicalExpireAt
→ 先返回旧数据
→ 尝试获取重建锁
→ 获得锁的线程异步查询数据库并更新缓存
```

逻辑过期适合能容忍短暂旧数据的商品展示、排行榜等场景。它以短时间旧数据换取高可用和更低的数据库压力。

逻辑过期不等于永远不设置物理 TTL。生产中可以设置远大于逻辑过期时间的物理 TTL，作为内存治理和异常兜底；Redis 也可能因内存淘汰或故障丢失 Key。

库存、余额、下单价格确认等强一致业务不能根据逻辑过期的旧缓存做最终决策。

## 5. 缓存雪崩

### 5.1 是什么

缓存雪崩是大量 Key 在同一时间集中失效，或 Redis 整体不可用，导致大量请求同时访问数据库。

```text
10 万个商品缓存都在 10:30 过期
  ↓
大量商品请求同时绕过 Redis
  ↓
数据库压力激增
  ↓
接口超时，故障扩大
```

Redis 宕机、网络故障等整体不可用场景，也会使所有缓存请求集中打向数据库。

### 5.2 方案一：TTL 加随机值

```text
基础 TTL：30 分钟
随机值：0 到 5 分钟
最终 TTL：30 到 35 分钟
```

让大量 Key 分散过期，避免同一时刻集中回源。

### 5.3 方案二：缓存预热

系统启动或大促开始前，提前加载热门商品详情到 Redis，避免活动流量到来后集中查询数据库并回填缓存。

### 5.4 方案三：高可用、限流与降级

- Redis 主从复制、哨兵或 Cluster，降低单点故障风险。
- Redis 或数据库压力异常时限流，限制继续涌入的请求。
- 对非核心展示请求进行降级，例如返回“商品详情加载中”，优先保护数据库和核心下单链路。

## 6. CloudMall 商品详情缓存选型

| 场景 | 风险 | 建议方案 |
| --- | --- | --- |
| 请求不存在商品 `P999` | 穿透到数据库 | 参数校验 + 空值缓存短 TTL；数据量大时加布隆过滤器 |
| 热门商品 `P001` 缓存过期 | 热点请求集中回源 | 互斥锁重建，或允许短暂旧数据时使用逻辑过期 |
| 大促大量商品缓存到期 | 大量 Key 同时失效 | TTL 加随机值 + 活动前预热 + 限流降级 |
| Redis 整体不可用 | 所有缓存失效 | Redis 高可用 + 限流降级，保护数据库 |

商品详情允许短时间读取旧展示数据时，可倾向逻辑过期；但库存、余额、订单金额确认仍应从数据库或对应强一致链路读取。

## 8. 面试表达

### 缓存穿透、击穿、雪崩有什么区别？

缓存穿透是大量请求查询不存在的数据，缓存和数据库都未命中，请求持续打到数据库；通过参数校验、空值缓存和布隆过滤器处理。缓存击穿是一个热点 Key 过期，大量请求同时回源数据库；可用互斥锁让一个请求重建缓存，或对可容忍旧数据的场景使用逻辑过期。缓存雪崩是大量 Key 同时失效或 Redis 整体不可用；通过随机 TTL、缓存预热、高可用和限流降级保护数据库。

### 热点商品缓存过期时如何避免数据库被打爆？

我会根据业务一致性要求选择互斥锁或逻辑过期。互斥锁让一个请求重建缓存，其他请求等待或短暂降级，适合希望尽快返回新数据的场景。商品展示允许短时间旧数据时，我会使用逻辑过期并异步重建，避免大量请求等待和集中访问数据库。锁需要设置过期时间和唯一 token，释放时校验 token。

### 为什么逻辑过期不适合库存扣减？

逻辑过期允许读取短时间旧缓存，适合商品详情展示；库存扣减、余额和订单金额确认需要基于当前真实数据决策。若使用旧库存做扣减判断，可能造成超卖或错误交易，因此必须走数据库条件更新或对应的强一致链路。
