## 2. Redis 是什么，为什么不能替代数据库

Redis 是内存型数据结构存储服务，常用作缓存，也可用于计数器、排行榜、去重集合和分布式协调等场景。

Redis 适合商品详情缓存：

- 数据主要保存在内存，访问延迟低。
- 商品详情通常读多写少，同一查询结果可被重复使用。
- 可以减少数据库的查询压力。

但 Redis 不能替代数据库作为商品、订单和库存的唯一数据源：

```text
数据库：最终可靠数据源，保存核心业务事实
Redis：缓存和加速层，数据可过期、淘汰或在故障中丢失
```

Redis 虽然支持持久化，但内存容量更有限、成本更高，且缓存本身允许存在短暂不一致。因此商品、订单、库存等核心数据仍以数据库为准。

## 3. 常用 Redis 数据结构

| 类型 | 适合场景 | CloudMall 示例 |
| --- | --- | --- |
| `String` | 一个值、JSON、计数器 | 商品详情 JSON、商品浏览量 |
| `Hash` | 一个对象的多个字段 | 商品名称、价格、状态的分字段缓存 |
| `List` | 有顺序的数据或简单队列 | 简单异步任务队列 |
| `Set` | 无序且去重的集合 | 用户已领取优惠券集合 |
| `ZSet` | 按分数排序的集合 | 商品热度排行榜 |

### 3.1 商品详情使用 String

商品详情通常需要整体读取、整体返回，可以优先缓存为 JSON 字符串：

```text
Key：product:detail:P001
Value：{"productCode":"P001","name":"机械键盘","price":299.00}
```

读取时只需要把 JSON 反序列化为商品详情 DTO，结构直观。

`Hash` 更适合频繁只更新局部字段的对象；如果商品详情每次都整体读取和返回，`String + JSON` 通常更简单。

## 4. Cache Aside 读流程

Cache Aside 的核心原则：应用代码负责先读缓存，缓存未命中时再读数据库并回填缓存。

```text
请求商品详情
  ↓
根据 productCode 查询 Redis
  ↓
缓存命中：反序列化 DTO，直接返回
  ↓ 缓存未命中
查询数据库
  ↓
数据库查到：写入 Redis 并设置 TTL
  ↓
返回商品详情
```

伪代码：

```java
String key = "product:detail:" + productCode;
ProductResponse cached = redis.get(key);

if (cached != null) {
    return cached;
}

ProductResponse product = productRepository.findByCode(productCode);
redis.set(key, product, ttl);
return product;
```

缓存命中时不访问数据库，缓存未命中时才从数据库查询并回填。

## 5. Cache Aside 写流程

商品信息更新时，数据库是最终数据源。常见流程：

```text
1. 更新数据库
2. 数据库事务提交成功
3. 删除对应 Redis 缓存
4. 下一次读取缓存未命中，从数据库读取最新数据并回填
```

例如商品 `P001` 改价：

```text
更新 products.price = 399
  ↓
DEL product:detail:P001
  ↓
下一次查询数据库得到 399，并重新写入缓存
```

### 5.1 为什么不建议先更新 Redis，再更新数据库

若先更新缓存、后更新数据库：

```text
Redis 更新成功
  ↓
数据库更新失败
  ↓
缓存中保留了数据库不存在的新数据
```

数据库和 Redis 是两个独立系统，双写无法天然原子完成。

### 5.2 为什么通常删除缓存而不是直接更新缓存

- 数据库是事实来源，删除后由最新数据库数据统一回填。
- 商品详情可能由多个字段、多张表或不同 DTO 组合，直接更新缓存容易漏字段或写错版本。
- 删除缓存的流程更简单，短暂不一致窗口也更容易控制。

Cache Aside 追求的是最终一致性，不是数据库与 Redis 的强一致性。

## 6. TTL 与缓存删除失败

缓存写入时需要设置 TTL，例如商品详情可以设置 30 分钟：

```text
product:detail:P001，TTL：30 分钟
```

TTL 的作用：

- 避免缓存永久保留旧数据。
- 控制 Redis 内存占用。
- 当删除缓存失败时，旧缓存仍会在过期后自动失效。

更新数据库后删除缓存失败的基础处理层次：

```text
数据库更新成功后删除缓存
  ↓ 删除失败
记录日志、告警、有限重试
  ↓
TTL 到期后旧缓存自动失效
  ↓
更高要求时：消息补偿或定时任务对账修复
```

“定时比较 Redis 与数据库”可以用于对账和修复，但不是最及时的基础手段；基础兜底是合理 TTL，加上删除失败的重试与告警。

## 7. CloudMall 商品详情缓存设计

### 7.1 Key 规范

```text
product:detail:{productCode}
```

示例：

```text
product:detail:P001
```

Key 使用业务前缀和商品编码，便于识别、排查和按业务批量管理。

### 7.2 Value 设计

缓存商品详情 DTO，而不是直接缓存数据库实体：

```text
ProductResponse
  ├── productCode
  ├── productName
  └── price
```

DTO 能限制对外暴露字段，也能避免数据库表结构变化直接影响接口缓存格式。

### 7.3 当前边界

- 商品详情是读多写少场景，适合 Cache Aside。
- 库存扣减、订单创建等强一致核心写操作不应只依赖普通商品详情缓存。
- 缓存穿透、击穿、雪崩和热点 Key 的专项处理将在后续学习中展开。

## 9. 面试表达

### Redis 为什么适合做商品详情缓存？

Redis 是内存型数据结构存储服务，访问延迟低，适合商品详情这类读多写少、查询结果可以重复使用的场景。商品详情缓存命中后可直接返回，减少数据库压力。但 Redis 是缓存和加速层，商品基础信息仍以数据库为最终数据源。

### Cache Aside 的读写流程是什么？

读请求先查询 Redis，命中则直接返回；未命中时查询数据库，将结果写入 Redis 并设置 TTL。写请求先更新数据库，事务提交成功后删除对应缓存，下次读取缓存未命中时从数据库回填最新数据。这种方式以数据库为准，达到最终一致性。

### 更新商品时为什么更新数据库后删除缓存？

如果先更新缓存、后更新数据库，数据库失败会使缓存出现数据库中不存在的新数据。数据库更新后删除缓存，下一次读取会从最新数据库数据回填，逻辑更简单。删除失败时通过日志、重试、TTL 和后续补偿降低旧缓存长期存在的风险。
