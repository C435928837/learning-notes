## 2. 为什么需要分布式锁

`synchronized`、`ReentrantLock` 和 `AtomicInteger` 只作用于当前 JVM。

```text
应用实例 A：synchronized(lockA)
应用实例 B：synchronized(lockB)
```

两个实例拥有各自独立的堆内存，`lockA` 与 `lockB` 不会相互感知。因此同一用户的重复下单请求落到不同实例时，两个本地锁不能阻止它们并发执行业务。

分布式锁将锁状态放在多个实例都能访问的共享协调服务中，例如 Redis：

```text
应用实例 A ─┐
            ├─ 竞争 Redis 中同一把锁
应用实例 B ─┘
```

谁获得锁，谁执行临界区；其他实例需要等待、重试或直接返回处理中的结果。

## 3. 原生 Redis 锁：正确获取

基础加锁命令：

```redis
SET lock:order:1001:activity:20260829 token-uuid NX PX 10000
```

| 部分 | 作用 |
| --- | --- |
| `lock:order:1001:activity:20260829` | 锁 Key，表达“用户 1001 在该活动中的下单处理” |
| `token-uuid` | 当前请求唯一标识，记录锁属于谁 |
| `NX` | Key 不存在时才设置成功，保证互斥 |
| `PX 10000` | 锁 10 秒后自动过期，避免持锁实例异常导致永久死锁 |

`NX` 和 `PX` 必须使用同一条 `SET` 命令。若先 `SETNX` 再单独设置过期时间，实例可能在两条命令之间崩溃，导致锁没有 TTL 而永久占用。

## 4. 为什么解锁需要 token 与 Lua

### 4.1 token 是锁持有者身份证

每个请求尝试获取锁前，生成一个唯一 token，例如 UUID：

```text
请求 A：token = a8f1...
请求 B：token = b7c2...
```

请求 A 成功加锁后：

```text
Key：lock:order:1001:activity:20260829
Value：a8f1...
TTL：10 秒
```

释放锁时，A 必须确认 Redis 中该锁的 Value 仍是 `a8f1...`。若已经变为 `b7c2...`，说明锁已过期并被 B 重新获得，A 不能删除。

### 4.2 直接 DEL 的问题

```text
T0：A 获得锁，开始创建订单
T10：A 执行过慢，锁过期
T11：B 获得新锁，开始创建订单
T15：A 结束，直接 DEL 锁
     → A 误删 B 正在持有的锁
T16：C 获得锁并进入临界区
```

此时 B 和 C 会并发执行业务。对于活动下单，可能出现多笔待支付订单、多扣活动资格、重复通知等问题。

`GET` 比较 token 后再单独 `DEL` 也不安全：`GET` 后锁可能过期并被 B 获取，A 的后续 `DEL` 仍会删除 B 的锁。

### 4.3 Lua 原子解锁

将“比较 token”和“删除锁”放进同一个 Lua 脚本：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end

return 0
```

```text
KEYS[1]：锁 Key
ARGV[1]：当前请求的 token
返回 1：锁仍属于当前请求，删除成功
返回 0：锁不存在或已属于其他请求，不能删除
```

Lua 脚本在 Redis 中原子执行，其他命令不能插入“比较”和“删除”之间。

## 5. 锁过期与 Redisson 看门狗

### 5.1 锁 TTL 的矛盾

```text
TTL 太短：业务未完成，锁先过期，其他请求可能进入临界区
TTL 太长：持锁实例异常后，其他请求等待太久
```

### 5.2 Redisson 看门狗

Redisson 的 `RLock` 可提供可重入分布式锁。使用不显式指定 `leaseTime` 的方式时，会使用看门狗自动续期：

```java
RLock lock = redissonClient.getLock("lock:order:1001:activity:20260829");

lock.lock();
try {
    createOrder();
} finally {
    lock.unlock();
}
```

```text
初始锁 TTL：通常约 30 秒，可通过 lockWatchdogTimeout 调整
持锁 Redisson 客户端正常运行且锁未释放：后台持续续期
业务结束并 unlock：立即释放锁，停止续期
应用宕机：看门狗停止，最后一次续期后的 TTL 到期后锁会释放
```

看门狗不理解“业务是否结束”，它只知道锁是否已经释放。业务结束后忘记调用 `unlock()`，只要应用仍正常运行，看门狗可能持续续期，导致其他请求长期拿不到锁。因此必须在 `finally` 中释放。

### 5.3 显式 leaseTime 的区别

```java
lock.lock(10, TimeUnit.SECONDS);
```

或：

```java
lock.tryLock(3, 10, TimeUnit.SECONDS);
```

显式指定 `leaseTime` 后，锁会在固定时长后自动释放，通常不使用看门狗自动续期：

```text
lock.lock()：不指定 leaseTime，使用看门狗续期
tryLock(waitTime, unit)：不指定 leaseTime，使用看门狗续期
lock.lock(leaseTime, unit)：固定时长自动释放，不自动续期
tryLock(waitTime, leaseTime, unit)：固定时长自动释放，不自动续期
```

即使使用看门狗，应用宕机、长时间 Stop-The-World GC、网络异常或 Redis 故障仍可能导致续期不及时。看门狗降低锁提前过期风险，但不能成为业务正确性的唯一保障。

## 6. CloudMall 场景选型

| 场景 | 首选方案 | 分布式锁的作用 | 最终边界 |
| --- | --- | --- | --- |
| 同一用户重复提交活动订单 | 幂等号或活动订单唯一约束 | 减少多实例并发重复处理 | `UNIQUE(user_id, activity_id)` |
| 热点商品缓存失效 | Redis 分布式锁 | 只允许一个请求回源数据库并重建缓存 | 重建失败时短暂降级或重试 |
| 秒杀库存扣减 | Redis Lua 或数据库条件更新 | 通常不是核心方案 | `stock >= quantity` 条件更新、订单幂等、补偿与对账 |
| 普通商品新增 | 数据库唯一约束 | 通常不需要 | 商品编码主键或唯一索引 |

### 6.1 重复下单的三层保护

```text
分布式锁：减少多个实例同时处理同一用户请求的竞争
订单幂等：识别并拒绝重复业务请求
数据库唯一约束：最终阻止重复订单落库
```

例如活动订单表可设计唯一约束：

```text
UNIQUE(user_id, activity_id)
```

即使 Redis 锁超时、故障转移、网络异常或调用重复，数据库仍拒绝同一用户在同一活动中创建第二笔订单。

### 6.2 为什么库存不能只依赖分布式锁

库存扣减需要保证“库存是否充足 + 扣减库存”不可分割。Redis Lua 脚本可以原子完成判断与扣减；数据库可使用：

```sql
UPDATE product_stock
SET available_stock = available_stock - ?
WHERE product_id = ?
  AND available_stock >= ?;
```

再通过受影响行数判断是否扣减成功。分布式锁会增加串行化等待和锁故障边界，不应替代库存原子扣减、订单幂等、补偿和对账。

## 8. 面试表达

### Redis 分布式锁为什么需要 NX、TTL 和 token？

`NX` 保证锁不存在时才获取成功，实现多个实例间互斥；TTL 避免持锁实例异常后锁永久占用；token 用于标识锁持有者，释放时必须确认锁仍属于当前请求。比较 token 与删除锁必须使用 Lua 原子执行，否则锁可能在两步之间过期并被其他请求获取，旧请求会误删新锁。

### Redisson 看门狗解决什么问题？

业务执行时间不可准确预估时，固定 TTL 可能在业务完成前过期。使用未指定 `leaseTime` 的 `RLock` 时，看门狗会在持锁客户端正常运行期间续期，降低锁提前释放导致并发进入的风险。它不理解业务是否结束，仍必须在 `finally` 中 `unlock()`；应用宕机、长时间 GC、网络异常等边界下也不能替代订单幂等和数据库唯一约束。

### 分布式锁能否完全解决库存超卖？

不能。分布式锁用于多实例互斥协调，但库存核心是“判断库存与扣减库存”的原子性。应使用 Redis Lua 或数据库 `stock >= quantity` 条件更新完成原子扣减，并通过订单幂等、失败补偿、库存回滚或对账保证最终一致性。分布式锁可用于缓存重建或降低重复处理竞争，但不应作为库存正确性的唯一保障。
