## 2. 主从复制

### 2.1 是什么

Redis 主从复制通常采用一主多从架构：

```text
客户端写请求
    ↓
主节点 Primary
    ↓ 异步复制
从节点 Replica 1、Replica 2
```

常规使用中，主节点负责写入，从节点复制主节点数据，并可承接部分对旧数据不敏感的读请求。

### 2.2 为什么需要

单个 Redis 节点存在单点故障风险，且读流量全部压在一个节点上。主从复制提供：

- 数据副本，降低单机故障风险。
- 读请求扩展能力，部分读流量可分发到从节点。
- Sentinel 自动故障转移和 Cluster 副本机制的基础。

### 2.3 如何同步

#### 初次连接：全量同步

```text
从节点连接主节点
→ 主节点生成 RDB 快照
→ 主节点发送快照给从节点
→ 从节点加载快照
→ 主节点再发送生成快照期间积累的写命令
→ 主从数据追上
```

#### 短暂断线后：增量同步

```text
从节点重连并告知已同步位置
→ 主节点从复制积压缓冲区查找缺失命令
→ 只发送断线期间遗漏的写命令
→ 从节点继续追上
```

若断线时间太长或主节点不再保留所需的复制积压数据，则需要再次全量同步。

### 2.4 异步复制的边界

主节点写入成功，不表示从节点已经完成同步：

```text
主节点写入成功并返回客户端
→ 主节点宕机
→ 最新写命令还未来得及复制到从节点
→ 故障转移后，新主节点可能缺少该数据
```

因此主从复制提高了可用性，但通常不保证强一致，也不能保证完全不丢数据。

CloudMall 中：

```text
商品详情展示：可在明确接受短暂旧数据时考虑读从节点
库存扣减、支付结果确认、订单状态确认：不能依赖可能延迟的从节点读结果做最终决策
```

订单、库存等核心事实仍应以数据库及对应的条件更新、幂等、补偿和对账方案为准。

## 3. Sentinel：自动故障转移

### 3.1 是什么

Sentinel 是一组独立的 Redis 监控和故障转移进程，不承担业务数据存储。

```text
Sentinel 1 ─┐
Sentinel 2 ─┼─ 监控主节点与从节点
Sentinel 3 ─┘

主节点 Primary  ←  从节点 Replica 1、Replica 2
```

应用通常使用支持 Sentinel 的 Redis 客户端，通过 Sentinel 获取当前主节点地址并在故障切换后重连。

### 3.2 Sentinel 做什么

1. 监控主节点和从节点的健康状态。
2. 多个 Sentinel 对主节点故障进行确认。
3. 从从节点中选出一个提升为新主节点。
4. 让其余从节点改为复制新主节点。
5. 向客户端发布故障转移事件，由客户端发现新主节点并重连。

### 3.3 为什么需要多个 Sentinel

只有一个 Sentinel 时，Sentinel 自己宕机或与其他节点网络隔离，就无法继续进行故障判断与自动故障转移。

多个 Sentinel 通过投票确认主节点故障，可以：

- 避免 Sentinel 自身单点故障。
- 降低单个 Sentinel 因网络抖动或自身异常导致误判的风险。
- 防止因单点误判而不必要地提升新主节点。

生产通常部署奇数个 Sentinel，例如 3 个，以便形成多数派判断。

### 3.4 Sentinel 的边界

| Sentinel 能解决 | Sentinel 不能解决 |
| --- | --- |
| 主节点故障后的自动故障转移 | 单主节点容量与写入能力的水平扩展 |
| 主从节点监控 | 异步复制导致的最后一小段数据丢失风险 |
| 客户端发现新主节点 | 故障切换期间的短暂不可用 |

Sentinel 是高可用方案，不是分片扩容方案。

## 4. Redis Cluster：分片扩容与副本故障转移

### 4.1 是什么

Redis Cluster 将 Key 分配到 `16384` 个哈希槽位，每个主节点负责一部分槽位：

```text
Key
  ↓ 计算哈希槽
slot 0 ~ 16383
  ↓
不同主节点分别负责一部分槽位
```

示例：

```text
主节点 A：slot 0 ~ 5000
主节点 B：slot 5001 ~ 10000
主节点 C：slot 10001 ~ 16383
```

每个 Key 只存储在负责该槽位的主节点。数据量或吞吐持续增长时，可增加分片并迁移部分槽位，实现水平扩容。每个主节点可配置副本节点，在主节点故障时参与故障转移。

### 4.2 Cluster 与 Sentinel 的区别

| 对比 | Sentinel | Cluster |
| --- | --- | --- |
| 核心目标 | 主节点故障自动转移 | 数据分片扩容 + 分片故障转移 |
| 数据分布 | 一主多从，主节点保存全量数据 | 多个主节点分别保存部分槽位数据 |
| 容量扩展 | 不能突破单主节点容量 | 可增加主节点和迁移槽位 |
| 高可用 | 依赖主从与多个 Sentinel | 每个分片可配副本节点 |

### 4.3 多 Key 操作边界与 Hash Tag

Cluster 中，多 Key 命令或 Lua 脚本涉及的多个 Key 必须落在同一个槽位，否则会被拒绝。

```text
product:stock:P001
order:pending:O001
```

这两个 Key 可能进入不同槽位。若确实需要多个 Key 进入同一槽位，可使用 Hash Tag：

```text
order:{1001}:detail
order:{1001}:status
```

Redis 只对 `{1001}` 计算槽位，因此两个 Key 会落到同一个槽位。

Hash Tag 应仅用于确实需要同槽位多 Key 操作的关联 Key。将大量无关 Key 固定到相同 Hash Tag 会造成数据和请求倾斜，削弱 Cluster 分片效果。

## 5. CloudMall 的 Redis 高可用边界

### 5.1 商品详情缓存

商品详情读多、允许短暂旧数据，数据量持续增长时可考虑 Cluster 分片扩容。读取从节点前，应明确业务是否能够接受复制延迟导致的短暂旧展示数据。

缓存实例故障或切换期间，应用层仍应：

```text
限流：限制继续涌入商品详情接口的请求量
降级：返回“商品详情加载中”或可接受的兜底展示数据
熔断：Redis 持续失败时暂时减少无效调用
预热/本地缓存：降低恢复时集中回源数据库的压力
```

### 5.2 核心业务链路

库存扣减、支付状态和订单状态确认不能因为缓存降级而使用旧数据做最终决策。应使用数据库条件更新、订单幂等、可靠消息、补偿和对账等方案保证业务正确性。

```text
Redis 高可用：降低 Redis 单点故障风险
应用层保护：避免 Redis 短暂不可用时压垮数据库
数据库与业务一致性设计：保证订单和库存正确性
```

高可用不等于强一致，也不等于完全不丢数据；三层能力不可互相替代。

## 7. 面试表达

### Redis 主从、Sentinel 和 Cluster 分别解决什么问题？

主从复制通过主节点写入、从节点异步复制提供数据副本和读扩展，但从节点可能存在复制延迟。Sentinel 监控主从节点，并在主节点故障时通过多个 Sentinel 投票确认故障、选举新主和通知客户端，因此主要解决单主架构的自动故障转移。Cluster 把 Key 分布到 `16384` 个槽位，由多个主节点分别负责一部分数据，因此同时解决数据分片、容量扩展、吞吐扩展和分片故障转移。Sentinel 不解决分片扩容，Cluster 的高可用也不等于强一致。

### 为什么主从复制仍可能丢数据？

主从复制通常异步进行。主节点写入成功并返回客户端后，如果在写命令复制到从节点前宕机，故障转移产生的新主节点可能没有这条最新写入。因此 Redis 高可用降低故障风险，但订单、库存等核心数据仍要依赖数据库和业务一致性方案。

### Redis 已高可用，为什么还需要限流和降级？

主从、Sentinel 和 Cluster 仍可能出现节点切换、网络异常、短暂不可用或缓存批量失效。若所有缓存请求同时回源数据库，可能触发级联故障。应用层应通过限流、熔断、降级、预热和本地缓存保护数据库；但库存和订单确认不能基于旧缓存做最终决策。
